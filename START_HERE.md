Этот архив содержит рабочий сайт, зафиксированную аналитику, объяснения решений и актуальное Python-ядро планирования. Начинать новый чат нужно с этого файла.

## Зафиксированный основной результат

- Исходный день: **204 из 205 заявок**, 31 активная бригада.
- После контрольной аварийной заявки: **205 из 206 заявок**, 32 активные бригады.
- Оба результата имеют `status = EXACT_VALID`, `publication_allowed = true` и `validation.status = VALID`.
- Единственная неназначенная исходная заявка: `SOUTHEAST-79450`.
- Отсутствие решения для неё после 7 072 проверок — предел локального поиска, а не доказательство глобальной невозможности.
- В веб-сайт уже встроены именно эти новые артефакты, а не старые 200/205.

## Главные продуктовые правила

1. Сначала максимальное покрытие заявок.
2. Затем минимальное число задействованных бригад.
3. Затем время реакции, пробег, дорога, ожидание и баланс.
4. Непроверенный или частичный быстрый кандидат нельзя выдавать за готовый план.
5. Никаких заглушек и заранее заготовленных объяснений.
6. Причины решений строятся детерминированно из ограничений и проверок алгоритма; LLM может только переформулировать уже доказанные факты.
7. Оператор должен видеть проблему, причину, действие и прямой переход к месту решения.

## Быстрый запуск сайта

Из корня архива:

```powershell
.\RUN_SITE.ps1
```

Скрипт использует готовый preview на `http://127.0.0.1:4174`. Если зависимости отсутствуют, он выполнит `npm install` по существующему lockfile. Новые production-зависимости не требуются.

Проверки сайта:

```powershell
cd site
npm run test:algorithm
npm run test:sites
npm run build
```

На момент упаковки: проверка алгоритмической интеграции прошла, API-тесты 8/8 прошли, production-сборка успешна.

## Основной алгоритм

Рабочий конвейер:

1. проверка входных данных;
2. построение быстрых локальных матриц;
3. поиск полного покрытия;
4. детальный последовательный расчёт маршрутов;
5. удаление только реально нарушающих порядок назначений;
6. точный ремонт прямыми вставками, перестановками и цепочками вытеснений;
7. повторная независимая проверка всего плана;
8. публикация только проверенного артефакта.

Код не содержит привязок к `SOUTHEAST-79450` или конкретной бригаде. Однако качество пока полноценно проверено только на одном дне, поэтому для доказательства устойчивости нужны прогоны ещё на 5–10 независимых днях.

Оценка времени для дня примерно на 205 заявок:

- те же адреса и прогретый кэш: 5–15 минут;
- новые адреса в тех же территориях: 20–60 минут;
- тяжёлый точный ремонт: до 60–90 минут.

Следующее безопасное ускорение без потери качества — параллельная проверка маршрутов разных бригад. Внутри одного маршрута переходы должны оставаться последовательными из-за зависимости времени отправления.

## Запуск Python-тестов

Создайте отдельное окружение Python и установите пакет из `algorithm/`. Затем:

```powershell
$env:PYTHONPATH = (Resolve-Path .\algorithm\src)
python -m pytest .\algorithm\tests -q
```

Для нового полного дня используйте `algorithm/tools/run_new_dataset_pipeline.py`. Пример параметров и ограничения описаны в `algorithm/routing_README.md`.

## Важная предпосылка маршрутизации

В архив включены датасет, статические матрицы, транспортный индекс и кэш запросов. Многогигабайтные OSM-плитки Valhalla не включены. Для новых автомобильных, пеших и велосипедных адресов должен быть доступен локальный Valhalla `/route` и `/sources_to_targets`. Для просмотра уже зафиксированного сайта Valhalla не требуется.
