# Архитектура и эксплуатация стенда

[Документация](../README.md) · [Архитектура](../reference/architecture.md) · [Инструкция VM](../../deploy/README_RU.md)

## Рабочая конфигурация

Текущий стенд `45.152.196.19` работает на Ubuntu 24.04: **4 vCPU, 8 ГБ RAM, диск 120 ГБ**. Внешний Nginx направляет запросы в Node API, приложение и Valhalla запущены через [deploy/compose.stand.yaml](../../deploy/compose.stand.yaml). Приложение слушает `127.0.0.1:8787`; Valhalla доступна во внутренней Docker-сети.

| Путь | Содержание |
| --- | --- |
| `/opt/beego/releases/<commit>` | Проверенный код и конфигурация релиза. |
| `/opt/beego/current` | Ссылка на активный каталог. |
| `/srv/beego/state/db/shifts.sqlite3` | Постоянная SQLite приложения. |
| `/srv/beego/state/runs`, `cache`, `replans` | Входы и артефакты расчёта, кэши и точные перепланирования. |
| `/srv/beego/routing/roads`, `transit`, `sources` | Установленные дороги, транспортный индекс и источники; приложение читает их без изменения. |
| `/etc/beego/stand.env` | `BEEGO_RELEASE_PATH`, `BEEGO_APP_IMAGE`, `BEEGO_VALHALLA_IMAGE` и пути volumes. |
| `/etc/beego/api.env` | Серверные настройки внешних сервисов, права `600`. |

Контейнер приложения работает от UID 1000; постоянные каталоги должны быть доступны этому пользователю. Вариант самостоятельного Node-процесса через systemd поддерживается как альтернативная установка и описан в руководстве VM; его пути нельзя смешивать с Docker-конфигурацией.

## Обновление релиза

1. Собрать и проверить код, установить источники с проверкой SHA-256, сформировать образ с ID коммита.
2. Проверить новый образ на отдельной QA-базе и свободном порту, с теми же дорожными источниками.
3. Создать согласованную SQLite-копию и сохранить прежние значения `stand.env`.
4. Указать новый образ и каталог релиза, проверить Compose и переключить приложение.
5. Проверить готовность, внешнюю страницу и сохранённый день; сравнить сохранность планов и фактов.

```bash
docker compose --env-file /etc/beego/stand.env \
  -f /opt/beego/current/deploy/compose.stand.yaml config --quiet
docker compose --env-file /etc/beego/stand.env \
  -f /opt/beego/current/deploy/compose.stand.yaml up -d --no-deps --wait app
curl -fsS http://127.0.0.1:8787/api/health
curl -fsS http://127.0.0.1:8787/api/runtime/readiness
```

`current` переключается на проверенный новый каталог после запуска. Откат возвращает предыдущий образ и каталог, сохраняя `state` и `routing`. Текущие планы, отзывы и история принадлежат постоянной базе.

## Резервирование

[backup-shifts.mjs](../../site/scripts/backup-shifts.mjs) открывает существующую SQLite в режиме `readonly`, без миграций и отмены активных задач, и использует SQLite backup API с учётом WAL. Пример из работающего Docker-стенда:

```bash
docker compose --env-file /etc/beego/stand.env \
  -f /opt/beego/current/deploy/compose.stand.yaml exec -T app \
  node scripts/backup-shifts.mjs .beego-data/backups/pre-release.sqlite3
```

Копия появится в `/srv/beego/state/db/backups/`; для постоянного архива задавайте уникальное имя и переносите файл на другой носитель. Проверяйте `PRAGMA integrity_check` и восстановление на отдельной базе. Артефакты `runs` и `replans` сохраняйте вместе с базой: они нужны для последующего точного пересчёта. Источники дороги восстанавливаются из проверяемого комплекта.

## Внешние сервисы

| Переменная | Функция |
| --- | --- |
| `GEOAPIFY_API_KEY` | Подсказки адресов и геокодирование. |
| `YANDEX_AI_API_KEY`, `YANDEX_AI_FOLDER_ID` | AI-помощник по снимку смены. |
| `YANDEX_RASP_API_KEY` | Обновление внешних железнодорожных источников. |
| `GEOAPIFY_ROUTING_API_KEY` | Явный выбор альтернативного дорожного провайдера. |

Ключи передаются только серверу. Стандартный стенд использует локальные Valhalla и транспортный индекс; контрольный расчёт работает без внешних ключей. После изменения `api.env` пересоздайте только приложение с `--force-recreate --no-deps --wait app`, чтобы обновить окружение. Проверьте подсказку безличного адреса и ответ AI через интерфейс; значения ключей в вывод не включайте.

## Готовность и ресурсы

`/api/health` подтверждает доступность процесса, `/api/runtime/readiness` — Python, канонический транспортный индекс и Valhalla. Новый расчёт проверяйте на отдельной QA-базе. Нагрузочные расходы определяются дорогой, количеством пар и размером артефактов; наблюдайте память, CPU, свободный диск и длительность задач.

В одном API-процессе один общий тяжёлый слот; просмотр продолжается во время расчёта. При горизонтальном масштабировании понадобится общая очередь. Для обработки клиентских данных подготовьте домен, HTTPS, аутентификацию с ролями, мониторинг и регулярное обновление транспортных источников. Настройка профиля в UI отвечает за отображаемые данные пользователя.

Команды сборки и проверки находятся в [разработке](../development/contributing.md), эксплуатационные сценарии — в [API](../reference/api.md).
