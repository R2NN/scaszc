# Интерактивная схема здания

Локальная ветка `codex/object-building-model` основана на `codex/dispatch-coverage-repair`, коммит `df88f04286bd1c9a3048a57cfedffea0fa96ce5d`. Отправка на GitHub не выполнялась.

## Что добавлено

В паспорте объекта есть вкладка **«Схема объекта»**. Она раскрывает широкий экран над существующей картой: процедурный разрез здания и карточку выбранного оборудования. Другие вкладки и исходное рабочее пространство сохраняются.

Рендерер получает секции, этажность, ширину, глубину, смещения крыльев, тип крыши, наличие подвала и размещение узлов. Код не привязан к списку домов или заранее нарисованным изображениям. Поддерживаются новые объекты, секции разной высоты, отдельные корпуса, одноэтажные здания, плоские, скатные и вальмовые крыши. Входная схема ограничена 80 секциями и 180 этажами на секцию.

На схеме доступны выбор мышью и клавиатурой, фильтр секций, масштаб и возврат к целому виду. Длинные здания открываются с крупного просмотра первой обслуживаемой секции; весь объект остаётся доступен через фильтр. Отдельная вкладка показывает сохранённый контур OSM. Панели адаптированы для светлой/тёмной темы и узкого окна.

Карточка оборудования использует существующие связи реестра: оборудование, условия доступа, заявки выбранного дня, относящиеся к нему особенности и историю визитов. Нажатие открывает исходную заявку или конкретный визит. Значок особенности не означает подтверждённую неисправность. Счётчик заявок строится из текущих заявок, а не задаётся в макете.

## Реальные и модельные сведения

Из исходных геокодированных объектов получены **177 контуров OpenStreetMap**, у **172** есть этажность. В снимке представлены значения от 4 до 25 этажей. Исходные теги и атрибуция сохранены в `site/server/data/building-osm.json`.

Для 18 объектов без точного контура из этого снимка используется детерминированная условная модель. Для пяти контуров без этажности значение также модельное. Это явно отражено в источниках схемы.

Условные секции не являются обмерным планом: входы OSM могут быть неполными или включать дополнительные двери. Габариты сложного контура не выдаются за точную глубину подъезда. Внутренняя планировка и стояки условные; этажные коробки имеют отметку «Модельная точка» и никогда не получают реальные клиентские связи по одному совпадению адреса.

Существующий технический инвентарь BeeGo тоже модельный. Новая схема не превращает его в подтверждённый инвентарь оператора. Онлайн-мониторинг и автоматическое определение неисправностей не подключены.

## Уточнение и новые здания

Кнопка **«Уточнить сведения»** открывает редактор секций и мест установки оборудования. Изменения сразу видны в предпросмотре; до сохранения база не меняется. Черновик сохраняется при закрытии формы и переключении вкладок, пока открыта страница, и может быть сброшен явно.

JSON-шаблон позволяет передать произвольную компоновку крыльев, включая угловые и разновысотные корпуса. Импорт проверяет этажи, размеры, дубликаты секций и принадлежность оборудования объекту. Можно импортировать шаблон в другой паспорт: идентификатор здания берётся из открытого паспорта, а чужие ссылки оборудования отклоняются.

Сервер хранит схемы и их версии отдельно в `building_models` / `building_model_history`. Для изменения нужны основание и актуальная ревизия: устаревшая форма получает HTTP 409. История изменений и исходная модель сохраняются.

Новые зарегистрированные через существующий импорт/форму объекты автоматически получают схему. Если геометрия и этажность неизвестны, оператор уточняет их в том же редакторе; добавлять ветки с новым адресом в рендерер не требуется.

API: `GET /api/buildings/:objectId`, `PUT /api/buildings/:objectId` (`model`, `expectedRevision`, `reason`, `actor`). Прямая ссылка на паспорт: `/?object=<objectId>&passport=building`.

## Проверка

Итоговый полный прогон: **359 тестов, 357 успешно, 2 пропущены, 0 ошибок**. Для Python-проверок использован `BEEGO_PYTHON=C:/Anaconda3/python.exe` с уже установленным OR-Tools. После заключительных правок повторно прошли 6 тестов схемы и production-сборка `pnpm build`.

Новые модульные проверки: `site/tests/building-model.test.mjs`. Они проверяют разнообразие источников, новые здания, разные высоты/крылья, некорректные импорты, изоляцию клиентских связей, версионность и отсутствие изменений плановых снимков.

Браузерный сценарий — `site/scripts/check-building-browser.mjs`. Он запускается через Playwright на отдельном локальном стенде, создаёт собственный профиль Chromium и не обращается к пользовательскому браузеру. Для него нужен установленный Playwright, доступный через обычное разрешение модулей либо `BEEGO_QA_MODULES`; production-зависимости не добавлены.

Проверка по умолчанию использует `http://127.0.0.1:4186`. Стенд должен иметь отдельный `BEEGO_DB_PATH`: сценарии временно меняют геометрию тестового паспорта и восстанавливают её, сохраняя журнал. Основной предпросмотр работает с другой БД и не получает эти изменения.

Браузерная проверка: **19 сценариев, 11 скриншотов, 0 ошибок JavaScript**. Отчёт, размеры окон и снимки: `docs/evidence/building-model/browser-report.json`. Помимо основного дома проверяются реальный 25-этажный объект, длинный дом, условные крылья 17/5 этажей и одноэтажный производственный корпус. Последние два — тестовые компоновки на отдельном стенде, а не фактические сведения о подписанном адресе.

Маршрутизатор, длительности, опубликованные планы, факты смены и оценки не изменяются. Новые зависимости не установлены. Сборка Sites и его worker остаются прежними; рабочий серверный API схем находится в локальном Node/Vite-сервере, как существующий API паспортов.
