# Интерактивная схема здания

Локальная ветка `codex/object-building-model` основана на `codex/dispatch-coverage-repair`, коммит `df88f04286bd1c9a3048a57cfedffea0fa96ce5d`. Отправка на GitHub не выполнялась.

## Что добавлено

В паспорте объекта есть вкладка **«Схема объекта»**. Она раскрывает широкий экран над существующей картой: процедурный разрез здания и карточку выбранного оборудования. Другие вкладки и исходное рабочее пространство сохраняются.

Рендерер получает секции, этажность, ширину, глубину, смещения крыльев, тип крыши, наличие подвала и размещение узлов. Код не привязан к списку домов или заранее нарисованным изображениям. Поддерживаются новые объекты, секции разной высоты, отдельные корпуса, одноэтажные здания, плоские, скатные и вальмовые крыши. Входная схема ограничена 80 секциями и 180 этажами на секцию.

На схеме доступны выбор мышью и клавиатурой, фильтр секций, масштаб и возврат к целому виду. Паспорт всегда открывается со всеми секциями целиком. Колёсико увеличивает/уменьшает схему в области указателя; кнопки масштаба сохранены. Отдельная вкладка контура удалена: он остаётся под секциями в увеличенном кликабельном навигаторе «Форма здания». Панели адаптированы для светлой/тёмной темы и узкого окна.

Карточка оборудования использует существующие связи реестра: оборудование, условия доступа, заявки выбранного дня, относящиеся к нему особенности и историю визитов. Нажатие открывает исходную заявку или конкретный визит. Значок особенности не означает подтверждённую неисправность. Счётчик заявок строится из текущих заявок, а не задаётся в макете.

## Реальные и модельные сведения

Из исходных геокодированных объектов получены **177 контуров OpenStreetMap**, у **172** есть этажность. В снимке представлены значения от 4 до 25 этажей. Исходные теги и атрибуция сохранены в `site/server/data/building-osm.json`.

Для 18 объектов без точного контура из этого снимка используется детерминированная условная модель. Для пяти контуров без этажности значение также модельное. Это явно отражено в источниках схемы.

Условные секции не являются обмерным планом: входы OSM могут быть неполными или включать дополнительные двери. Габариты сложного контура не выдаются за точную глубину подъезда. Внутренняя планировка и стояки условные; этажные коробки имеют отметку «Модельная точка» и никогда не получают реальные клиентские связи по одному совпадению адреса.

Существующий технический инвентарь BeeGo тоже модельный. Новая схема не превращает его в подтверждённый инвентарь оператора. Онлайн-мониторинг и автоматическое определение неисправностей не подключены.

## Уточнение и новые здания

Кнопка **«Уточнить сведения»** открывает редактор секций и мест установки оборудования. Изменения сразу видны в предпросмотре; до сохранения база не меняется. Черновик сохраняется при закрытии формы и переключении вкладок, пока открыта страница, и может быть сброшен явно.

JSON-шаблон позволяет передать произвольную компоновку крыльев, включая угловые и разновысотные корпуса. Импорт проверяет этажи, размеры, дубликаты секций и принадлежность оборудования объекту. Можно импортировать шаблон в другой паспорт: идентификатор здания берётся из открытого паспорта, а чужие ссылки оборудования отклоняются.

Сервер хранит схемы и их версии отдельно в `building_models` / `building_model_history`. Для изменения нужны основание и актуальная ревизия: устаревшая форма получает HTTP 409. История изменений и исходная модель сохраняются.

Новые зарегистрированные через существующий импорт/форму объекты автоматически получают схему. Если геометрия и этажность неизвестны, оператор уточняет их в том же редакторе; добавлять ветки с новым адресом в рендерер не требуется.

API: `GET /api/buildings/:objectId`, `PUT /api/buildings/:objectId` (`model`, `expectedRevision`, `reason`, `actor`). Прямая ссылка на паспорт: `/?object=<objectId>&passport=building`.

## Проверка

Итоговый полный прогон: **367 тестов, 365 успешно, 2 пропущены, 0 ошибок**. Для Python-проверок использован `BEEGO_PYTHON=C:/Anaconda3/python.exe` с уже установленным OR-Tools. После заключительных правок повторно прошли 18 целевых тестов схемы, планировок, подсветки и паспорта и production-сборка `pnpm build`.

Новые модульные проверки: `site/tests/building-model.test.mjs`. Они проверяют разнообразие источников, новые здания, разные высоты/крылья, некорректные импорты, изоляцию клиентских связей, версионность и отсутствие изменений плановых снимков.

Браузерный сценарий — `site/scripts/check-building-browser.mjs`. Он запускается через Playwright на отдельном локальном стенде, создаёт собственный профиль Chromium и не обращается к пользовательскому браузеру. Для него нужен установленный Playwright, доступный через обычное разрешение модулей либо `BEEGO_QA_MODULES`; production-зависимости не добавлены.

Проверка по умолчанию использует `http://127.0.0.1:4186`. Стенд должен иметь отдельный `BEEGO_DB_PATH`: сценарии временно меняют геометрию тестового паспорта и восстанавливают её, сохраняя журнал. Основной предпросмотр работает с другой БД и не получает эти изменения.

Браузерная проверка: **30 сценариев, 16 скриншотов, 0 ошибок JavaScript**. Отчёт, размеры окон и снимки: `docs/evidence/building-model/browser-report.json`. Помимо основного дома проверяются реальный 25-этажный объект, длинный дом, условные крылья 17/5 этажей и одноэтажный производственный корпус. Последние два — тестовые компоновки на отдельном стенде, а не фактические сведения о подписанном адресе.

Маршрутизатор, длительности, опубликованные планы, факты смены и оценки не изменяются. Новые зависимости не установлены. Сборка Sites и его worker остаются прежними; рабочий серверный API схем находится в локальном Node/Vite-сервере, как существующий API паспортов.


## Источники и достоверность

| Сведения | Откуда берём сейчас | Достоверность |
| --- | --- | --- |
| ID, адрес, вид работы, окно заявки | Исходный набор хакатона, сохранённые данные BeeGo | Генератор схем не создаёт эти заявки; принадлежность реальному производственному потоку этим не подтверждается |
| Координаты / OSM ID | Ранее геокодированный исходный набор | География, не технический инвентарь |
| Контур | 177 объектов OSM, снимок 18.10.2026 | В навигаторе «Форма здания» — геометрия источника. Разрез приближает очертания секциями; для сложного фасада упрощение бывает существенным |
| Этажность | 172 тега OSM `building:levels`; остальные 23 объекта — модель/данные карточки | Число для здания целиком не подтверждает равные высоты крыльев |
| Год | `start_date` у 134 контуров | Публичная метка, не обследование |
| Крыша | `roof:shape` у 54 контуров | При отсутствии — модельное допущение |
| Подъезды | Старый синтетический реестр + неполные входы OSM | Нумерация не подтверждена; блоки разреза называются секциями |
| Внутренние стены, помещения, лестницы, лифты, подвал | Согласованные синтетические профили по назначению/этажности | Совпадение с настоящим домом внутри не установлено |
| Стояки, коробки, разводка | Синтетическая модель сети | Не данные сети Билайна |
| Узлы и связи с заявками | Существующий синтетический инвентарь `complexity-v2` | Связи последовательны, но наличие оборудования в настоящем здании не подтверждено |
| Доступ и история работ | Существующий симулятор этапов / записи стенда | Стартовая история и условия синтетические; ручные записи не переписываются |
| Неисправность онлайн | Источник не подключён | Значок особенности не является сигналом мониторинга |

Синтетика проверяется на согласованность: помещения входят в габариты, профиль определяет лестницы/лифты, коробки входят в диапазон стояка, реальные связи не присваиваются пассивным точкам. Типовые этажи повторяются осмысленно; первый этаж и подвал могут иметь отдельные планы.

## Подробный формат v2

`sections[].outline` — локальный полигон секции в метрах; `rotation` — поворот крыла. `floorPlans.typical` содержит полигоны помещений `spaces` и ломаные стен `walls`; `floorPlans.overrides` задаёт индивидуальные этажи. `risers` задаёт положение/диапазон стояка и конкретные `boxFloors`.

`placements` задаёт существующий ID узла, секцию, этаж, координаты `x/z` как доли ширины/глубины и связанный стояк. `cables[].points` задаёт явную трассу: секция, локальные метры `x/z`, высотная отметка в этажах. Такие координаты сохраняются при импорте, сохранении и загрузке; тесты проверяют, что они не заменяются шаблоном.

Разрез и новый **«План этажа»** читают одну модель. Автопрофиль заполняет только отсутствующий план. Старые схемы v1 получают явно модельные значения по умолчанию.

Пример `site/public/examples/building-model-import.json` полностью синтетический: корпуса 12/5/1 этаж, повёрнутое крыло, индивидуальный шестой этаж, полигональное техпомещение, кабельная трасса. Можно открыть кнопкой «Уточнить сведения → Синтетический пример здания» или загрузить через «Импорт JSON» и увидеть предпросмотр. Пример сам не сохраняется в базе; «Сбросить» возвращает исходную схему. Пример не описывает настоящий дом по адресу открытого паспорта.

Для реальной внутренней точности нужны планы/обследование и техническая топология оператора. Адрес, этажность и заявки этих сведений не содержат. Схема показывает переданную структуру; PDF/BIM не распознаёт. Это не обмерный CAD-чертёж: точная толщина стен, высоты каждого перекрытия, проёмы и сложная кровля не моделируются как в BIM.


## Навигация и выделение проблем

«Форма здания» расположена рядом со схемой, а в узком окне — под ней. Подсказка «Нажмите на секцию», номера, hover/focus и кнопка «Показать все секции» делают переходы явными. Текущая секция жёлтая. Действующие записанные проблемы дают красную пульсацию всем явно связанным секциям; у текущей проблемной секции сохраняется жёлтая рамка. При reduced motion пульсация отключается.

Область проблемы определяется ID узла, оборудования, линии, подъезда либо всего объекта. Поддерживаются явные `affectedEntityIds` / `affectedSectionIds`; общая проблема с несколькими связями отмечает каждую секцию. Закрытые, истёкшие, будущие и положительные записи, а также общие правила операций не становятся красными неисправностями. Это визуализация записей обслуживания, а не подключение мониторинга. Проверочный общий инцидент в `navigator-shared-problem.png` подставлен только в ответ браузера автотеста; база основного стенда не менялась.

План этажа показывает помещения, общие зоны, техпомещения, лестничные марши, символы лифтов, шкафы и заданные кабельные отрезки уровня. Для синтетических помещений рисуются условные дверные проёмы; у импортированных планов сохраняются переданные полигоны и стены. Размер текста и шкафов учитывает масштаб SVG. Надпись об OSM убрана из постоянной метастроки; источники и ограничения по-прежнему доступны в раскрывающемся разделе.


## Перетаскивание и квартира клиента

Левой кнопкой мыши можно передвигать увеличенный разрез и план этажа по двум осям; колёсико меняет масштаб относительно курсора. Начальное открытие по-прежнему вмещает все секции. Перемещение начинается после порога 5 px, перехватывает указатель и не выбирает оборудование при отпускании кнопки. Обычный щелчок и клавиатурный выбор сохраняются.

На разрезе квартира клиента обозначена только компактной фиолетовой точкой со значком дома. Нажатие мышью или Enter/Пробел сразу открывает нужный план этажа; полигон квартиры и подпись показываются только на этом плане. Карточка показывает номер исходной заявки, квартиру, секцию и этаж. «На плане этажа» открывает ту же квартиру на её уровне; отдельная кнопка возвращает к исходной заявке. При нескольких заявках можно выбрать нужного клиента. При открытии паспорта из заявки используется её ID.

Демо-привязки создаются детерминированно только для примеров подключений, локальных заявок и дозаказов явно синтетического реестра `complexity-v2`, через уже связанный с заявкой узел. Это новые синтетические данные, а не сведения OSM или реальные квартиры абонентов; в карточке видна пометка «Демо-привязка». Они сохраняются в модели отдельно от операционных заявок. Для нового/реального обращения без привязки показывается «Расположение квартиры не указано», без случайной отметки.

«Уточнить сведения → Квартиры клиентов» позволяет задать секцию, этаж, номер квартиры и конкретное помещение плана. Сохранение требует основания и актуальной ревизии, источник становится `operator`. JSON здания поддерживает:

```json
{
  "customerLocations": [{
    "orderId": "SOUTHCENTER-46513",
    "sectionId": "section-1",
    "floor": 3,
    "spaceId": "room-1",
    "unit": "9",
    "source": "synthetic"
  }]
}
```

Для реальных данных ставится `source: "import"` или `"operator"`; доступны только существующие помещения типа `apartment` / `office`. `spaceId` выбирается в плане соответствующего этажа, включая индивидуальные планы. Чужая секция, отсутствующее помещение и этаж за пределами здания отклоняются. Повторный ID заявки запрещён. Старые JSON без `customerLocations` работают с пустым списком.

Рендерер также принимает явное поле `order.buildingLocation` с теми же координатами и источником (кроме `orderId`, он берётся из заявки). Такая привязка имеет приоритет перед модельным списком. Для сквозного получения этого поля из внешней CRM нужен контракт интеграции; текущий общий CSV-импорт автоматически квартиру по адресу не определяет. Номер квартиры сам по себе не даёт её положения внутри дома: для точного отображения нужен ID помещения, привязанный к реальному плану.

Автопроверки на отдельной базе проверяют панорамирование обоих видов, отсутствие случайного выбора при перетаскивании, единый полигон квартиры, клавиатуру, переход в заявку, неизвестное расположение и сохранение ручного уточнения после перезагрузки. Основная база предпросмотра этими проверками не меняется.
