# Рейтинг, разбор отзывов и подбор состава

[Документация](../README.md) · [Пользовательский сценарий](../features/ratings.md) · [API](api.md#rating)

## Оценка выполненной работы

Один завершённый визит получает один отзыв. Сервер определяет исполнителя по сохранённой версии плана и факту завершения. Звёзды, текст, дата, адрес и ID визита связываются с этим специалистом. Каталог показывает число оценок, средний балл, распределение звёзд и сглаженный рейтинг:

```text
score = (sum(included stars) + 20 × 4.20) / (included count + 20)
```

В контрольном каталоге 35 штатных и 1000 резервных профилей. Резерв наследует операционный профиль существующего специалиста: территорию, старт, смену, транспорт, навыки, оборудование и лимиты маршрута. Рейтинг и история качества в начальном наборе синтетические; новые отзывы по подтверждённым визитам записываются через API.

## Разбор отзыва

Путь диспетчера: **отзыв → подробности визита → переписка и вложения → решение → рейтинг до/после**. Реализованы результаты:

| Результат | Влияние |
| --- | --- |
| Отзыв обоснован | Оценка участвует в рейтинге. |
| Претензия не к работе инженера | Оценка исключается; исходные звёзды и текст сохраняются. |
| Подтверждена ошибка клиента | Оценка исключается с основанием. |
| Оценка уточнена клиентом | Сохраняются исходные и новые звёзды, согласие клиента, способ и описание подтверждения. |

Для решения обязательны основание и ответ инженеру. Запись выполняется транзакционно: меняются участие/оценка отзыва, ревизия обращения, версия рейтинга, история решения и переписка. `expectedRevision` защищает от сохранения поверх чужого решения. Завершённый разбор можно открыть повторно. Флаг связи с клиентом сохраняет поручение в решении; автоматический звонок и CRM-очередь не подключены.

## Условия и подтверждение

Нижняя и верхняя границы рейтинга задаются числами или ползунками: `1 ≤ qualityFloor ≤ qualityCeiling ≤ 5`. Пул `staff` использует штат, `all` — расширенный каталог. Предложение содержит конкретных людей, оценки, профили, навыки, потребность и дефицит. Ручные закрепления сохраняют исполнителей; исключения из диапазона отражаются явно.

`POST /api/ratings/scenarios` с `kind: staffing` создаёт `AWAITING_CONFIRMATION`. Изменение параметров позволяет получить новое предложение. При подтверждении сервер заново сверяет:

- ревизию и SHA исходного плана;
- отпечаток заявок и состава;
- версию рейтинга и пожелания клиентов;
- доступность и список предложенных инженеров.

Только после этого `/confirm` фиксирует `approvedEngineerIds` и занимает общий вычислительный слот. Устаревшее предложение нужно подобрать заново.

## Проверка маршрутов

Поиск пробует освободить целого инженера переносом его визитов в другие маршруты. Каждая изменённая поездка рассчитывается на момент выезда, затем проверяется весь план, включая общий склад. Неуспешный перенос отбрасывается целиком. В текущем коде локальный этап ограничен 36 дорожными проверками и 40 секундами; серверный бюджет 150 секунд включает подготовку индекса.

После сокращения маршрутов состав сопоставляется с утверждёнными профилями и диапазоном рейтинга. Один человек учитывается один раз. Пожелания клиентов применяются как мягкие предпочтения после обязательных ограничений. Результат содержит использованный состав, назначения, очередь и дефицит по профилям. Ручное переназначение также проходит дорожную проверку.

Доступны состояния `AWAITING_CONFIRMATION`, `RUNNING`, `READY`, `FAILED`. Результаты и настройки сохраняются в `rating_scenarios`; `save` отмечает готовый полный реальный сценарий. Операционный день публикуется через собственный механизм смены. Условный профиль «+1 специалист» предназначен для сравнения потребности и не добавляет сотрудника в реестр.

## Прогноз нагрузки

«Ожидаемая нагрузка» использует [ml-demand-forecast.json](../../site/public/data/ml-demand-forecast.json). Дата прогноза и период обучения показаны в интерфейсе. Структура выбранного проверенного дня помогает распределить спрос по территории и навыку. Производительность берётся из рассчитанных маршрутов; резерв оценивается по разнице верхнего и среднего спроса. Для профиля без наблюдаемой производительности показывается неоценённая потребность. Прогноз состава служит подготовкой к адресному планированию.
