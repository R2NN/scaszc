# Архитектура и эксплуатация стенда

[Документация](README.md) · [Главный README](../README.md)

## Компоненты

![Архитектура BeeGo: интерфейс, Node API, операции, Python и данные маршрутизации](assets/system-architecture.svg)

Клиент — React/Vite с картой MapLibre. Node.js API выдаёт данные, хранит смены и запускает Python-расчёт. SQLite работает с WAL и транзакционными версиями планов. Valhalla запущена локально. AI и Geoapify используют серверные переменные окружения; секреты не попадают в репозиторий или клиентскую сборку. PDF строится детерминированно из сохранённых данных и доступен без AI.

`GEOAPIFY_API_KEY` включает поиск адресов и `/api/geocode/suggest`. Он не должен автоматически выбирать Geoapify для дорожной проверки: этот режим задаётся отдельно через `GEOAPIFY_ROUTING_API_KEY`. На стенде используется локальная Valhalla и локальный индекс общественного транспорта. После изменения `/etc/beego/api.env` перезапустите `beego-api.service` и проверьте поиск по безличному тестовому адресу; значение ключа не выводите в логи и не добавляйте в Git.

Один API-процесс даёт один слот расчёта. Второй пользователь во время вычисления получает `429 PLANNING_BUSY`; интерфейс остаётся доступным для просмотра. Это рассчитано на небольшой демонстрационный стенд. Несколько API-процессов без общего замка нарушили бы гарантию одного вычисления.

## Раскладка VM

| Путь/сервис | Назначение |
| --- | --- |
| `/opt/beego/releases/<commit>` и `/opt/beego/current` | Версионированный код и атомарное переключение релиза |
| `/srv/beego-data/shifts.sqlite3` | Постоянная операционная база |
| `/srv/beego/offline-assets/` | Дорожные и транспортные данные, включая недельные снимки |
| `/srv/beego/.venv` | Python-окружение алгоритма |
| `/etc/beego/api.env` | Серверная конфигурация и ключи, доступ только администратору |
| `beego-api.service`, `nginx`, `beego-valhalla` | API, публичный прокси и маршрутизатор |

Подробные команды и установка снимков — в [deploy/README_RU.md](../deploy/README_RU.md). Публичный IP стенда динамический. Перед обработкой настоящих клиентских данных нужны домен, HTTPS, аутентификация и политика доступа; нынешний адрес предназначен для демонстрации.

## Проверки

Из `site/` после установки зафиксированных зависимостей:

```powershell
pnpm install --frozen-lockfile
pnpm run build
pnpm run test:algorithm
pnpm run test:sites
node --test tests/planning-slot.test.mjs tests/shift-operations.test.mjs
```

Проверить сервер: `GET /api/health`, затем статус основной базы `GET /api/base-data/status`. Поиск адресов проверяется через `GET /api/geocode/suggest?q=Москва%2C%20Тверская` и `POST /api/geocode` с безличным тестовым адресом: оба запроса должны вернуть результат `provider: geoapify`, а не `GEOAPIFY_NOT_CONFIGURED`. Сборка интерфейса подтверждает наличие клиентской и серверной частей, но новый план проверяется отдельно. Для недельного комплекта есть тесты `algorithm/tests/test_install_weekly_rail_snapshots.py` и `algorithm/tests/test_transit_index_dates.py`; на стенде дополнительно проверен успешный расчёт небольшой смены для 18.08.2026.

## Резервирование и восстановление

База находится вне релиза, поэтому смена версии кода не заменяет состояние смен. Команда `pnpm run backup:shifts` создаёт согласованную SQLite-копию; её надо хранить отдельно от VM и периодически проверять восстановление. Незаконченный расчёт после перезапуска можно повторить; опубликованный план остаётся сохранённым. Недельный транспортный архив проверяется установщиком по контрольным суммам и устанавливается идемпотентно.

## Ограничения мощности

Одновременно выполняется **один** тяжёлый расчёт, остальные запросы обслуживаются параллельно на чтение. На текущем стенде выбраны 4 vCPU, 8 ГБ RAM и SSD 50 ГБ: это конфигурация для демонстрации и текущих локальных данных, не измеренная гарантия пропускной способности. При росте числа расчётов сначала измеряют память Valhalla, длительность задач и I/O; затем увеличивают ресурсы или выносят очередь и маршрутизатор. Размер базы и снимков следует мониторить.
