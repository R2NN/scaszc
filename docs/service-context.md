# Повторные обращения и общие проблемы

Обе функции используют существующий паспорт и общую карту BeeGo. Планировщик, рейтинг, факты визитов и алгоритмы аварийных выездов не меняются.

## Где открыть

- В заявках появился фильтр «Повторные» и отметки у связанных заявок.
- Паспорт объекта → «Обращения»: основание повтора, счёт, симптом, история, исходные заявки, подготовка следующего выезда, ответственный, срок и готовность доступа/оборудования/клиента.
- Справа от оформления карты — «Сеть». В списке общих событий доступны фильтр по наличию заявок, регистрация проблемы и импорт/экспорт.
- Нажатие события или его обозначения на карте открывает одну карточку с разделами «Заявки», «Причина», «История». Нумерация заявок одинакова в карточке, на карте и в выделенном списке слева. Пунктир включается отдельно: это зависимость, не физическая кабельная трасса.
- Обычные компоненты не загромождают карту. Реестр доступен в свёрнутом блоке. Близкие обозначения событий группируются; группа открывает список для выбора конкретного события. Событие без координат остаётся доступным в списке, координаты не выдумываются.

## Работа с данными

Первоначально контекст пуст. «Показать демонстрационный пример» явно создаёт учебные записи для текущих заявок. Все такие записи помечены как демонстрационные; они не являются историей этих клиентов или сигналами реального оборудования. Условное положение учебного узла подписано отдельно. Пример доступен только для пустого набора.

Настоящее повторное обращение связывается диспетчером с выбранной заявкой после проверки стабильного лицевого счёта/ID подключения и симптома. Один адрес, имя или соседство на карте не создают связь. По счёту можно найти обращения из более ранних сохранённых смен и явно связать их при совпадении симптома. Демонстрационные случаи в этот поиск не входят. Ссылки на исходные заявки открывают соответствующую дату в отдельной вкладке. История визитов объекта доступна отдельно и сама по себе не доказывает, что визиты относятся к одному клиенту.

Плановый второй этап отличается от неустранённой проблемы и не попадает в фильтр повторных неудачных обращений. Завершение визита не означает устранение симптома. Автоматических штрафов в рейтинге нет.

Общую проблему можно зарегистрировать вручную. Поддерживаются оборудование, линия/кабель, питание, ухудшение качества связи, плановые работы и общий доступ. Ограничение доступа имеет отдельный тип и не объявляется сетевой аварией. Диспетчер задаёт основание зависимости и конкретные заявки. Наличие обращений не обязательно.

Подготовка решения записывает отметку в истории и открывает редактируемую форму нового окна клиента в существующем перепланировании. Пока оператор не проверит и не опубликует черновик, расписание не меняется. Кнопка не создаёт дубликат заявки и не означает отправку инженера. Для нового наряда используется существующее добавление заявки.

## JSON и API

`GET /api/service-context?shiftId=<полный ID смены>` возвращает `revision`, `cases`, `incidents`, `components` и разрешённые ссылки `priorCases`.

Экспорт из интерфейса содержит:

```json
{
  "schemaVersion": 1,
  "shiftId": "ID из экспорта вашей смены",
  "date": "2026-08-17",
  "data": { "cases": [], "incidents": [], "components": [] }
}
```

Начните с экспорта нужной смены. Импорт заменяет только её контекст, сохраняя версию в журнале. Используйте полные `order.id` этой смены; сокращённые номера не принимаются. Координаты компонента имеют формат `[широта, долгота]` и необязательны. Переданные точные значения сохраняются, генератор их не заменяет.

Общие поля: уникальный `id`, текст `title`, `provenance` (`operator`, `import`, `demo`). У события нужны `componentId`, `type`, `status` (`review`, `confirmed`, `resolved`), `orderIds`, текст `basis`, `updatedAt`. `observedAt` хранит время исходного сигнала отдельно от редактирования карточки. История: массив `{at, text, actor?}`.

У обращения обязательны `accountRef`, `symptom`, `identityConfirmed: true`, `orderIds`, `basis`, `updatedAt`, `status` (`unresolved`, `returned`, `no_access`, `planned`, `resolved`). Необязательные `previousCases: [{shiftId, caseId}]` разрешаются сервером только на более ранние реальные обращения того же региона, счёта и симптома.

Подготовка `task`: строковые `action`, `owner`, `deadline` (пустая строка либо `YYYY-MM-DDTHH:mm`), а также `access`, `equipment`, `customer` со значениями `unknown`, `waiting`, `ready`.

`PUT` передаёт `{revision, shiftId, date, data, actor}`. `PATCH` передаёт `{revision, kind: "case" | "incident", id, action: "task" | "status" | "note", task? , status?, note?, actor}`. Несовпадение версии возвращает 409; невалидный импорт — 422, без частичного сохранения. Ограничения: файл до 2 МБ, до 500 записей каждого типа, до 300 событий истории записи.

## Хранение и ограничения

Штатно создаются отдельные таблицы `service_contexts` и `service_context_history` в настроенной операционной SQLite. Запись контекста не обновляет `shifts`, `plan_versions`, `visit_facts`, dispatch или rating. Локальные базы в Git не добавляются.

Реального подключения к мониторингу/CRM Билайна нет. Это рабочий интерфейс для зарегистрированных вручную или импортированных событий и явно подтверждённых связей. Текущая доступность оборудования не измеряется; отсутствие новых сигналов не считается признаком исправности. Автоматический подбор причин, массовая отмена заявок и автоматическая отправка бригад отсутствуют намеренно.

## Проверка

`node --test tests/service-context.test.mjs` проверяет изоляцию планов, область смены, сохранение после перезапуска, конфликты версий, атомарность импорта, разные типы проблем, неизвестные координаты и связи с прошлыми обращениями. Полный набор: `node --test tests/*.test.mjs`; сборка: `npm run build` из `site`.

Браузерные изменения проверяются с отдельным `BEEGO_DB_PATH`, а не с рабочей базой пользователя.


Воспроизводимая браузерная проверка: `node scripts/check-service-context-browser.mjs` из `site` при `BEEGO_QA_ISOLATED=1`, `BEEGO_QA_URL=http://127.0.0.1:<порт отдельного стенда>`. `BEEGO_QA_MODULES` может указывать на каталог `node_modules` с установленным Playwright, `BEEGO_QA_OUTPUT` — на папку результатов. Скрипт проверяет карту, видимость номеров поверх маркеров и между панелями, подготовку, ручное обращение, тип проблемы, выпадающие списки, JSON, тёмную тему и мобильную ширину. Он временно меняет только контекст на тестовом стенде, восстанавливает исходный контекст и сравнивает всю опубликованную смену до/после. Рабочую базу для этого скрипта использовать нельзя.
