## Что добавлено

Первичный точный конвейер, авторитетные durationSnapshot, допуски, снабжение, дорожный стек, барьер публикации, карта и существующие уведомления переиспользованы. Новых production-зависимостей нет; hosting-конфигурация сохранена.

**Старт.** `START_CHANGED` проверяет дату, подтверждение и источник координат, время доступности, отсутствие начатого дня. Адаптер формирует стартовую точку в нормализованных данных, сохраняет `common/start_points.json` с происхождением и включает его в контрольную сумму. Первичный/событийный поиск и независимый валидатор получают одну и ту же точку. Старые входы сохраняют офисный старт. Возвращение в офис не добавлено.

**Состояние.** `operationalState.js` используется UI и сервером: момент, часовой пояс, revision, статус, текущий визит, координаты, источник, время оценки и доступность. До/после смены, недоступность, ожидание, движение, работа и свободное состояние различаются. Фактически начатая незавершённая работа имеет приоритет над анимацией. При превышении планового конца без фактического окончания расчёт требует уточнения, не объявляет инженера свободным.

**Перехват.** Python `dispatch.py` вычисляет воспроизводимую точку на реальной полилинии по доле её длины. Это допущение `SCENARIO_ROUTE_LENGTH`, не GPS. Пройденные геометрия, время и метры сохраняются в `movements`, входят в стоимость и следующую цепочку. Для автомобиля исходное направление передаётся Valhalla с heading/tolerance/radius/search_cutoff. [Параметры Valhalla](https://github.com/valhalla/valhalla/blob/master/docs/docs/api/route/api-reference.md). При общественном транспорте действует консервативная политика: закончить текущее плечо до прежнего места назначения и только затем перенаправить; высадки между остановками нет. Работа сохраняется до завершения. Ожидание до начала работы допускает перенос ещё не начатого визита с проверкой всей смены.

**Поиск.** Рассматриваются все допущенные инженеры территории. Сначала проверяются прямые назначения всем кандидатам, затем перестроение будущего в затронутой территории. Неподходящие/недоступные состояния исключаются с причиной. Уже начатые услуги, ручные закрепления и другие территории сохраняются. Авария должна быть первой будущей услугой выбранного инженера после текущей начатой работы. Это отдельно проверяет валидатор. Есть общий лимит 5000 проверок маршрутов; первый проход — до 400 на инженера, расширение — до 1000. Один процесс использует существующий planning slot и общий предел 15 минут. Готовые проверенные варианты доступны до окончания поиска; принятие останавливает оставшуюся работу.

**Хранение/API.** Миграция 3 создаёт `dispatch_incidents`, `dispatch_sessions`, `dispatch_preferences`. Есть context, sessions, incidents, policy, clock, states, accept/retry/cancel/read. `eventKey` предотвращает дубли. Полный вариант содержит план, вход, хеш, отчёт валидатора и стабильный ID. Python сохраняет исходную JSON-сериализацию; Node не пересериализует checksummed artifact, чтобы не менять каноническое представление float.

**Приём решения.** По умолчанию включена изменяемая политика 300 секунд. Дедлайн отсчитывается с создания события, хранится сервером и не зависит от x60. Сценарные часы останавливаются на аварии до решения; это явное допущение демонстрации. Реальный таймер продолжает идти. Сервер сам воспроизводит сценарные часы между запросами браузера. После рестарта прерванный поиск возвращается в очередь с прежним дедлайном.

Перед публикацией транзакция повторно проверяет revision, план, факты, состав, модели, условия, историю длительностей, снимки и ожидающие аварии. Несовпадение ставит задачу на новый расчёт. Ручное и автоматическое принятие идут через один `startPreview → completePreview → publish`; терминальное решение идемпотентно. Другой инцидент инвалидируется после новой публикации и пересчитывается от актуальной смены. Если проверенного варианта нет, сохраняются ошибка, эскалация и повторный поиск; фиктивного назначения нет.

**Политика выбора:** меньше неназначенных аварий → меньше остальных неназначенных заявок → меньше задействованных за день инженеров → раньше начало работы на новой аварии → меньше общий пробег. Рейтинг не влияет на допуск. Опыт считается по известным на момент события завершённым аварийным визитам `duration_visits`, версии дедуплицируются. Клиентских оценок в источнике нет: показано «Нет оценок», оценки не придуманы.

**Интерфейс.** «Аварии» внутри «Хода смены», существующий Notification UI с явным типом `EMERGENCY_INCIDENT`, переход в нужную смену, карта MapLibre в единственном экземпляре, легенда до/после, отдельное подтверждение. Видны ETA/выезд/дорога, покрытие, затронутые визиты, нагрузка и доступный до конца дня резерв. Подробности и маршруты раскрываются в общей прокрутке. Резерв здесь — доступные сейчас инженеры без будущей незавершённой работы, а не просто никогда не использованные за день инженеры.

Поддержан воспроизводимый сценарный режим. Фактическая работа после планового окончания требует уточнения, а не выдуманного остатка.
- Реальные длительные дорожные прогоны выполнены для домашнего старта и одной аварии в отдельных ручной/автоматической сессиях. Последовательные/конкурирующие аварии и крайние состояния дополнительно проверены автоматическими тестами; отдельный реальный дорожный прогон двух одновременных аварий не выполнен.
- Не заявляются GPS-точность интерполяции, точный исторический поезд/метро и глобальный оптимум ограниченного поиска. SLA для аварии не придуман: показано время реакции и клиентское окно из исходного контракта.

## Восстановление

На этой машине новый согласованный backup лежит в `A:/BeeGo-tz3-emergency-dispatch/runtime/qa/tz3/release.sqlite3`. Для отдельного восстановления скопировать **этот автономный файл**, выбрать новый BEEGO_DB_PATH и свободный порт, собрать `site` и запустить:

```powershell
cd A:/BeeGo-tz3-emergency-dispatch/site
$env:BEEGO_DB_PATH='A:/BeeGo-tz3-emergency-dispatch/runtime/qa/tz3/ui.sqlite3'
$env:BEEGO_PYTHON='A:/BeeGo-final-object-complexity/.venv/Scripts/python.exe'
$env:VALHALLA_ROUTE_ENDPOINT='http://127.0.0.1:8002/route'
$env:PORT='4200'
pnpm build
node server/main.mjs
```

Нужны совместимый Python с зависимостями проекта, pnpm, Valhalla и транспортный индекс (не входят в gzip планов). После clone локальной рабочей БД/кешей не будет: их восстанавливают из локального backup, а не из Git. Для новых событий после восстановления нужны также runtime/exact-replans с метаданными исходного dataset/cache; они сохранены в рабочем кандидате. Архивные gzip позволяют отдельно проверить старый результат, но не заменяют transport/runtime.

Прежняя версия доступна на 4199 и не требует отката. Для независимого восстановления — новый worktree от `beego-before-tz3-20261017`, отдельная копия `A:/BeeGo-final-handoff/pre-tz3-20261017/candidate-release.sqlite3`, отдельный порт. Подробности исходной передачи — `A:/BeeGo-final-handoff/ROLLBACK_BEFORE_TZ3.md`. Не выполнять reset чужого дерева и не соединять старый код с новой БД.
