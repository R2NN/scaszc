# BeeGo: перенос обновлений в существующую версию сокомандника

Инструкция для агента на другом компьютере. Задача — объединить новые функции и оформление с уже работающей версией сокомандника, сохранив его изменения, данные и настройки запуска.

## 1. Что именно передаётся

Репозиторий: https://github.com/R2NN/scaszc

Ветка передачи: `codex/network-design-integration`.

Предыдущая передача, относительно которой выделены изменения: `codex/beego-complete-runtime`, коммит `df597ee03c0afd440536967764251b77ba9d476a`.

**Один коммит с кодом для переноса:**

```text
1c7f67803554ad494df3143e7dc4159e269b43f6
```

Его родитель — `df597ee`. В нём собран итоговый diff 34 файлов между предыдущей передачей и проверенной версией `0d159049cd31d3e81de5dc2d0f0219cf783b4cb0` из `codex/video-scenarios-qa`. Дерево файлов этого коммита совпадает с проверенной версией. Следующий коммит в ветке содержит только эту инструкцию.

Переноси именно указанный коммит с кодом. Не применяй дополнительно промежуточные коммиты `41e4fec..0d15904`: иначе одни и те же изменения попадут повторно. Исходные ветки сохранены.

В diff нет изменений `algorithm/`, Dockerfile, Compose, дорожных/транспортных ресурсов, зависимостей и lock-файлов. Базы, секреты, локальные кэши и данные пользовательских смен не передаются. Это обновление существующего приложения, а не установка другой копии вместо версии сокомандника.

## 2. Подготовка и перенос

Выполняй команды из корня **репозитория сокомандника**. Сначала прочитай его `AGENTS.md`, `site/AGENTS.md` и инструкции текущей версии.

```sh
git status --short
git branch --show-current
git remote -v
git log -5 --oneline
```

Зафиксируй исходную ветку и SHA сокомандника. Если есть незакоммиченная работа, сохрани её отдельным локальным коммитом с осмысленным составом файлов; не включай БД, `.env`, кэши и секреты. Не делай reset/clean и не перезаписывай рабочую папку архивом.

Проверь, что `origin` указывает на `https://github.com/R2NN/scaszc.git`. Если у сокомандника другой origin, сохрани его и добавь отдельный remote для этого URL; в дальнейших командах используй имя этого remote вместо origin.

```sh
git fetch origin codex/network-design-integration
git show --stat 1c7f67803554ad494df3143e7dc4159e269b43f6
git merge-base HEAD 1c7f67803554ad494df3143e7dc4159e269b43f6
git merge-base --is-ancestor df597ee03c0afd440536967764251b77ba9d476a HEAD
```

Последняя команда возвращает 0, если предыдущая передача входит в историю сокомандника. Если нет — изучи общий предок и отличия, особенно наличие строительной схемы, операций со сменами, рейтинга и полного runtime. Не подменяй его версию нашей ради устранения конфликтов. При переименованных модулях перенеси соответствующие изменения в их новые места. Если недостаёт существенной базовой функции, укажи конкретную зависимость и согласуй её включение.

Если указанный коммит уже является предком HEAD, не применяй его повторно. Если новая функциональность частично перенесена другим способом, сверяй поведение и добавляй только недостающее.

Создай интеграционную ветку **от текущей версии сокомандника** (если такое имя уже занято, выбери свободное):

```sh
git switch -c codex/integrate-network-design
git cherry-pick 1c7f67803554ad494df3143e7dc4159e269b43f6
```

Если возникли конфликты, сохрани обе группы доработок и совмести их по смыслу. Затем добавь конкретные разрешённые файлы через `git add <путь>` и выполни `git cherry-pick --continue`. Не используй массовое «взять нашу/их версию» для `App.jsx`, серверных API или CSS. Отмена незавершённого переноса: `git cherry-pick --abort`.

Не переключай рабочую ветку сокомандника на ветку передачи. Не делай force push. После переноса проверь diff относительно записанного исходного SHA сокомандника: должны сохраниться его собственные функции и появиться только согласованные обновления.

## 3. Что должно появиться после объединения

- **«Сеть: влияние на заявки».** Иконка без текста на общей подложке режимов карты, сразу после времени. На обычной карте видны проблемные узлы и предупреждения у связанных заявок. Режим сети приглушает остальные заявки, домики и маршруты, выделяя источники, связанные заявки и пунктирные зависимости.
- **Контекст события.** Две вкладки: «Заявки» и «История». Источник, статус «Проверяется / Подтверждена / Устранена», ожидаемое восстановление или «Неизвестно», необязательный скрываемый комментарий. Для заявки — «Можно выполнять / Ждать восстановления», «Открыть заявку», «Пересмотреть план». Кнопки и текст одного масштаба; карточка шире, адаптивна, с анимацией появления/закрытия.
- **Понятное действие диспетчера.** Отметки по заявкам носят рекомендательный характер. «Пересмотреть план» открывает существующий черновик переноса клиентского окна выбранной заявки; расчёт и публикация выполняются отдельно. Занятый или сохранённый актуальный черновик защищён от перезаписи. Открытие заявки сохраняет карточку контекста.
- **История.** Записи действий создаются автоматически, новые сверху, сначала восемь с раскрытием остальных. Кнопки «Обновить» нет. Нет обязательного поручения из четырёх полей и отдельной вкладки «Причина».
- **Паспорт объекта.** «Обзор / Схема объекта / Визиты / Особенности». Схема расширяется на рабочую область справа от левого меню, закрывая календарь и кнопки карты; переход как в рейтинге, 420 мс, с поддержкой уменьшенного движения. Компактная карточка отступает от верхних кнопок. Визиты по умолчанию охватывают все виды работ; архивные планы отделены от подтверждённых измерений.
- **Остальное оформление и исправления.** Крестики без фона в «Ход смены», «Перепланирование», «Отчёт PDF», «Аналитика»; календарь хода смены по центру окна; инженеры остаются на истинных координатах при масштабировании; домики на обычной карте поверх узлов. В свёрнутом списке бригад раздела заявок и в деталях назначенной заявки показан транспорт инженера.
- **Исправления приёмки.** Корректная стартовая точка инженера для выбранного дня; нормализация навыков и пояснений в аналитике; защита уже начатого выезда от несовместимого переноса окна; корректный MIME `.mjs` для PDF; резервное копирование без изменения активных расчётов; отсутствие самопроизвольного восстановления аварийного демосценария в новом сеансе браузера.

Повторные обращения отключены в интерфейсе. Старые `cases`, поручения и совместимые API сохраняются ради чтения ранее записанных данных; не возвращай их как новую видимую функцию.

## 5. Данные, календарь и сохранность

Сетевой контекст хранится в новых SQLite-таблицах `service_contexts` и `service_context_history` той же рабочей БД. API создаёт их через `CREATE TABLE IF NOT EXISTS`; отдельный SQL-файл для миграции не требуется. Если у сокомандника есть собственный механизм миграций, согласуй создание таблиц с ним. Не создавай новую БД вместо действующей.

Перед первым запуском обновлённого сервера сделай согласованную резервную копию рабочей SQLite, учитывая WAL. Для остановленного приложения допустимо копирование файлов; для работающего используй SQLite backup API. Исправленный `site/scripts/backup-shifts.mjs` читает БД в readonly и не запускает миграции/инвалидацию активных расчётов. Из `site`, передав фактические пути:

```powershell
$env:BEEGO_DB_PATH = 'D:\BeeGoData\shifts.sqlite3'
node scripts/backup-shifts.mjs 'D:\BeeGoBackups\before-network-integration.sqlite3'
```

Эти пути — пример; сначала найди реальную БД сокомандника. Для Docker используй его существующую процедуру резервного копирования тома/SQLite.

Контракт: `GET /api/service-context?shiftId=...`; изменения через `PATCH` с `revision`. Конфликт версий — 409; неверные данные — 422 без частичного сохранения. Контекст не заменяет `shifts`, версии плана, факты выездов, рейтинг или аварийный dispatch. Связи задаются явными ID заявок и основанием, не вычисляются из близости на карте. Указанные в данных координаты контекста имеют формат `[широта, долгота]`; MapLibre требует соответствующего преобразования.

Автоматические три учебных узла с шестью связанными заявками появляются только на исходном московском наборе **17.08.2026**, при совпадении ID, адресов и координат. На произвольных данных сокомандника пустой список событий может быть корректным. Не добавляй фиктивные сбои в его рабочие данные ради демонстрации. Для показа используй отдельную тестовую БД с исходным набором или явно зарегистрированные тестовые события. Живой мониторинг оператора не подключён.

Время исходного сигнала относится к дню события и не меняется при редактировании. Серверное время записи действия — настоящее, с подписью «Записано» в истории; это не дата исторического сигнала. Ручное время события необязательно и проверяется относительно выбранного дня. Оценка восстановления может выходить за пределы дня смены. Не подменяй текущим числом все даты и не переписывай аудит датой тестовой смены.

## 6. Сборка и запуск на компьютере сокомандника

Не меняй его рабочий способ запуска, `.env`, ключи, порты, тома и настройки маршрутизации. В этом обновлении нет новых зависимостей. При установленном Node и уже подготовленном runtime команды из `site`:

```sh
node --version
npm run build
node --test tests/*.test.mjs
```

Требование проекта — Node не ниже 22.13; передаваемый код проверен на Node 24.14.1. Если зависимости ещё не установлены, установи их штатным способом репозитория с его lock-файлом. Не обновляй версии попутно. Запускай тесты из `site`, а не из корня репозитория.

При запуске через Node останови/перезапусти только процесс приложения сокомандника после backup и сборки. `npm run start:server` выполняется из `site`, с его прежним `BEEGO_DB_PATH`, окружением маршрутизации и `PORT`. Vite preview сам по себе не заменяет операционный API.

При Docker сохрани **прежние имя Compose-проекта, набор compose-файлов и параметры запуска**. Если он уже использует `compose.complete.yaml`, обновление приложения обычно выполняется так из корня, с подстановкой его реального имени проекта:

```sh
docker compose -p EXISTING_PROJECT -f compose.complete.yaml up -d --build app
docker compose -p EXISTING_PROJECT -f compose.complete.yaml ps
docker compose -p EXISTING_PROJECT -f compose.complete.yaml logs --tail 100 app
```

`EXISTING_PROJECT` — не новое предлагаемое имя. Иное имя/папка проекта может подключить новые пустые тома и создать впечатление потери данных. Не выполняй `down -v`, factory reset или prune. Если сокомандник использует другую конфигурацию, адаптируй его штатную команду, не замещай её этой.

Проверь `http://127.0.0.1:<его-порт>/api/health` и `/api/runtime/readiness`: для работы точного расчёта нужен `ready: true`. Если runtime не готов, проверь конкретные отсутствующие ресурсы по `docs/RUN-COMPLETE.md`; не подменяй проверенные маршруты фиктивными и не считай отображение страницы подтверждением работоспособности расчёта.

## 7. Приёмка после слияния

Изменения проверены до передачи; эти результаты не заменяют проверку версии сокомандника **после** объединения. В его интеграционной ветке сборка и автоматические тесты должны пройти заново. У передаваемого исходного кода ранее прошли 403 Node-теста, 2 пропущены (405 всего), и сборка; при изменениях сокомандника количество тестов может отличаться.

На отдельной тестовой БД пройди сценарии:

1. Обычная карта: проблемные узлы видны до открытия «Сети», связанные заявки отмечены; домики не теряются под источником. При переключении режима обычные элементы приглушаются, узлы/заявки/связи выделяются; выход восстанавливает обычное оформление.
2. Выбери один из трёх учебных узлов: номера и ID заявок совпадают в карточке и на карте, показаны только его зависимости. Скрытие/включение связей работает. Перемещение карты и кнопки масштаба сохраняют выбор; пустое поле снимает выбор с анимацией и без движения камеры. Нет подписи demo под маркером и отвергнутого длинного перелёта камеры.
3. «Открыть заявку» сохраняет контекст. Статус, ожидаемое восстановление, комментарий и решения по выездам сохраняются после перезагрузки; дублирующее сохранение не плодит историю. Есть состояния ошибки/занятости. История обновляется после действий автоматически.
4. «Пересмотреть план» открывает перенос окна нужной заявки. До отдельной публикации исходный план не меняется. Действующий черновик не затирается. Уже начатый выезд защищён; допустимый будущий перенос рассчитывается и публикуется штатным точным механизмом.
5. Паспорт: компактная карточка ниже верхних кнопок, схема расширяется с сохранением видимого левого меню и закрывает календарь/контролы. Визиты показывают реальные имеющиеся записи и отдельно архивные планы; план не становится фактом. «Особенности» работает с условиями обслуживания. Проверь светлую/тёмную темы и узкий экран.
6. «Ход смены»: календарь остаётся в центре окна, инженеры не разъезжаются при отдалении; слежение работает при включённом «Следить за бригадой». Транспорт соответствует профилю, неизвестный не превращается в автомобиль. Крестики рабочих областей без фона и сохраняют данные.
7. Регрессии версии сокомандника: рейтинг, импорт, сохранённые смены, факты, перепланирование, PDF с предпросмотром. Открытие новой вкладки браузера не заменяет рабочую смену аварийной демонстрацией. Если пересекался код аварий/расчёта, проверь реальное получение и принятие валидного предложения на изолированном сценарии.

В ветке есть браузерные скрипты: `site/scripts/check-service-context-browser.mjs` и `site/scripts/check-shift-marker-browser.mjs`. Для них нужны доступный пакет Playwright и Chrome. Первый рассчитан на неизменённый исходный демонстрационный набор, адаптация допустима только под эквивалентные проверяемые сценарии. Оба запускай на отдельном локальном тестовом сервере, не на рабочей БД. Скрипт маркеров может управлять демонстрационными часами.

Пример окружения из `site` после подготовки отдельного тестового сервера:

```powershell
$env:BEEGO_QA_ISOLATED = '1'
$env:BEEGO_QA_URL = 'http://127.0.0.1:4193'
$env:BEEGO_QA_OUTPUT = 'D:\BeeGoQA\network'
# Если Playwright установлен отдельно:
# $env:BEEGO_QA_MODULES = 'D:\qa-tools\node_modules'
node scripts/check-service-context-browser.mjs
```
