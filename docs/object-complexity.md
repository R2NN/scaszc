# Переменная длительность и паспорт объекта

Рабочая ветка реализует пункт 2 финального ТЗ. База: `main` на `02d4811a93a1e17d6a45364a8a705e0f93fc6053`. Исходные материалы и нормативы сохранены. Главный день — 17.08.2026, Europe/Moscow.

## Расчёт

Единственная формула находится в `site/server/durationModel.mjs`. React запрашивает серверный предпросмотр. Python получает проверяемый снимок, а не собственную копию формулы.

Техническая база: подключение 60, локальные работы 30, дозаказ 10, авария/информация 80 минут. Оформление — соответственно 10, 0, 10, 0, 0. Все 21 исходные пары группы и подтипа из `work_rules.csv` сохраняются. Информация не превращается в аварию из-за группы или оснащения. Ориентир дороги 20 минут не добавляется к визиту.

База включает обычную подготовку и одну стандартную операцию. Подтверждённые дополнительные устройства, точки, площадки, сегменты, кабельные работы, локализация, замена, первоначальное обновление и значимый подъём меняют относящуюся к ним техническую часть. Пригодная существующая линия и известное место неисправности сокращают время. Оформление не масштабируется. Доступ сверх обычной подготовки — отдельный измеренный компонент.

`K = technical / baseTechnical`. Визит — `technical + documents + access`. Снимок хранит базу, факторы, источники, компоненты, историю с ID и ревизиями наблюдений, версию, момент расчёта, округление и итог. Единицы — целые минуты, минимум технической работы 1 минута. Подтверждённый большой состав суммируется без скрытого потолка. Ошибочные количества отклоняются с объяснением.

Ручное время — отдельный `durationOverride: { minutes, reason }`. Оно сохраняется при повторном расчёте и журналируется. Вернуться к автоматическому времени существующей заявки можно сценарием изменения длительности. Оба действия изменяют смену через расчёт, сравнение и явную публикацию.

Начальные веса — гипотезы команды. Рабочий блок «Ограничения → Нормативы времени» сохраняет технические минуты, оформление, веса, политику истории, дату действия и новую версию в SQLite. Остальные настройки ограничений остаются предпросмотром. Сохранение модели не переписывает опубликованные планы.

## Пригодные факты и область применения

Есть устойчивые ID объекта, подъезда, узла, оборудования и линии. Дом определяется исходным ID геокодера/локации, а не текстом адреса или округлением координат. Новая подтверждённая точка получает серверный UUID; объединение с существующим объектом выполняется явно. Связи узел–подъезд и линия–узел проверяются.

Начало и окончание дают длительность всего визита. Технический факт известен только при известных отдельных этапах доступа, оформления и ожидания клиента. Пустой этап не считается нулём. Непригодный/исключённый факт не обучает модель. Исправления добавляют ревизию, исполнитель сохраняется за фактическим визитом.

Причина неизвестна, разовое ожидание клиента и «другое» не становятся свойствами дома. Для переноса установленной причины оператор выбирает конкретную сущность или сопоставимую операцию и основание. Минимум — три пригодных наблюдения. Область узла влияет только на работу с посещением этого узла. Частная линия и подъезд не влияют на соседей. Изменение области закрывает прежнее условие с сохранением истории. Временное условие имеет срок и действие «Больше не актуально».

История считается по сопоставимому составу работ и установленной причине. Из факта вычитается исходная оценка факторов без истории; при новой версии базы используется сопоставимая база новой версии. Берётся медиана, проверяются выбросы по абсолютной границе и MAD, применяется сглаживание `n / (n + s)`. Выбирается одна наиболее конкретная подтверждённая область на компонент. Техническая и измеренная доступная части не дублируются. Поправка работает в обе стороны и не накапливается при повторном расчёте.

При расчёте учитываются только известные к этому моменту ревизии фактов, завершившиеся визиты, подтверждения и сроки. Старые прогнозы остаются неизменяемыми.

## Алгоритм и публикация

Длительность попадает в `Job.service_duration_min`: допуск пары, CP-SAT, материализацию, ремонт, временные ограничения, последовательные переезды, событийное перепланирование и метрики. Python проверяет SHA содержимого снимка, единицы и совпадение минут; независимый валидатор дополнительно сверяет `authoritative_duration_min` и расписание.

API первоначального плана пересчитывает все заявки на сервере. Результат получает серверную квитанцию, связанную со всеми заявками, снимками, ресурсами и расписанием. Подмена или удаление снимка/минут/маршрута при сохранении отвергается. Черновик пересчитывается сервером и повторно проверяется при публикации. Прошлые и начатые визиты сохраняют исходное время и назначение. Клиентское окно ограничивает начало, а не обязательно окончание.

Старые сохранённые смены мигрируют без замены опубликованного плана. Неизменённые старые визиты сохраняют норматив; явный пересчёт создаёт новые снимки. Старая БД не переинициализируется. Новый план с другими минутами не получает старый статический артефакт. Совпадающий упакованный кандидат переиспользуется только при полном совпадении значимых входов.

## Интерфейс

«Время на объектах» — тематический режим того же экземпляра MapLibre. Камера, дата, тема, территория и выбранный маршрут сохраняются. В этом режиме близкие объекты объединяются в группы с числом объектов, нажатие раскрывает группу. В маршрутах и заявках кластеров нет. Отдельные точки показывают минуты; зелёный означает быстрее норматива минимум на 10 минут, жёлтый — разницу меньше 10 минут, красный — дольше минимум на 10 минут, серый — недостаточную историю. Рядом со списком есть короткая легенда. Открытие паспорта из списка или с карты сохраняет камеру; приближение выполняется отдельной кнопкой «Показать на карте». Доступный расчёт выводится сразу, история подгружается заранее и повторно используется для той же даты, вида и объёма работ. В интерфейсе нет коэффициента K. По умолчанию показано время для вида работ из заявки каждого объекта; выбор конкретного вида позволяет сравнить одинаковые работы. Панель использует тот же контейнер, ширину, отступы, заголовок, кнопку закрытия и анимацию, что и «Заявки». После закрытия она открывается кнопкой режима «Время на объектах», сохраняя фильтры и камеру. Можно сравнить состав заявок либо стандартный объём: один прибор, точка, площадка и сегмент.

История посещений показывает таблицу «План / Факт»: выполнение работ, получение доступа, оформление и ожидание клиента, затем «Всего на объекте». В итог не входит дорога. Для прежних записей, где отдельные минуты оформления и ожидания не сохранены, показана их общая измеренная разница; неизвестные этапы остаются неизмеренными.

Поиск обслуживаемого адреса не зависит от наличия заявки на текущий день. Карточка объекта открывается из карты, заявки, маршрута и аналитики. Паспорт содержит три раздела: «Обзор», «Визиты», «Особенности». В обзоре показаны время работы и оформления, посещения и действующие особенности; расчёт и оборудование раскрываются отдельно, история изменений находится в особенностях. Оборудование свёрнуто; внутренние ID и постоянные пояснения механики скрыты. Первые шесть объектов списка загружаются заранее, наведение и фокус также запускают загрузку. Адрес и оценка из списка видны сразу. Кэш деталей разделяется по объекту, дате, виду и объёму работ и очищается при изменении смены, истории или нормативов. Новая история обновляет тематический источник карты, а не создаёт новый canvas.

«Точность времени работы» в «Аналитика → Эффективность» сравнивает технические минуты модели и фиксированной базы на одних пригодных фактах последующего периода. Показаны средняя ошибка в минутах, число проверенных визитов и количество случаев, когда работа заняла больше или меньше плана. Подробности проверки свёрнуты.

PDF и JSON-экспорт используют снимки той же сохранённой версии. Плановые дорога, километры и затраты не выдаются за измеренный факт. Сохранённые PDF остаются отдельными артефактами.

## Импорт

CSV, JSON, XLSX и XLS используют общее сопоставление и проверку. Дополнительные необязательные поля:

| Поле | Значение |
| --- | --- |
| `duration_factors` | JSON, например `{"line":"existing","devices":1}` |
| `duration_override` | JSON `{"minutes":85,"reason":"Согласован дополнительный объём"}` |
| `service_entities` | JSON с существующими `object`, `entrance`, `node`, `line` |
| `object_id` | ID объекта из реестра |

Старые файлы поддерживаются. Исходные минуты сохраняются как источник, но произвольное значение старого файла не становится новым нормативом: сервер рассчитывает время по известному виду работ и исходному сценарию. Для намеренной ручной длительности нужен `duration_override` с причиной. Обновлён скачиваемый шаблон заявок.

Генератор сохраняет исходные 205 ID, адреса, координаты, виды и ресурсы. Реестр содержит 195 объектов, раздельные подъезды, узлы, оборудование и линии. Исторические визиты имеют отдельные ID. Встречаются богатая, малая и пустая история, быстрые и сложные работы, неизвестные причины, пропуски, редкие тяжёлые случаи, действующие и устранённые условия доступа.

Истинные этапы генерируются отдельно от прогноза: скрытые свойства операций/объектов, отдельные случайные события, измеренные этапы. Генератор факта не возвращает прогноз плюс шум. Инвентарь синтетический, точки оборудования не геокодированы. Это выборка визитов, а не полная измеренная транспортная история смен. Начала/окончания в выборке не пересекаются у одного исполнителя. Разделение для главного дня: обучение до 01.08.2026, проверка с 01.08 до 17.08. Прогноз каждого визита рассчитан до его результата. Параметры и ограничения записываются в `manifest.json`, измерения — в `quality.json`.

Верхний manifest включает две дополнительные точки стресс-набора (197 суммарно); основной реестр — 195 объектов, 1780 визитов. Исправления и исключения сохраняют прежние ревизии. Параметр другой опорной даты сдвигает даты набора и границу последующего периода; фиксированный транспортный индекс при этом сам не становится историческим доказательством для другой даты.

После реальной материализации и независимой проверки компактный экспорт создаётся командой из корня:

```powershell
node site/scripts/package-complexity-plan.mjs runtime/new-sample/input.json algorithm/artifacts/complexity/initial-exact.json
```

Переупаковка метаданных с сохранёнными дорожными доказательствами допустима только после `algorithm/tools/seal_duration_plan.py`: инструмент требует совпадения всех длительностей и повторяет независимую проверку всего расписания. При изменении минут нужна новая материализация.

Для ограниченного приёмочного поиска доступны `BEEGO_REPLAN_ROUTE_CHECKS` (штатно 400) и `BEEGO_REPLAN_TIMING_QUERIES` (штатно 24). Уменьшение бюджета может оставить заявки с явным `SEARCH_BUDGET_EXHAUSTED`; оно не доказывает невозможность назначения. Переезды не заменяются оценкой при недоступном маршрутизаторе.

Для чистого повторения браузерного сценария укажите новый `BEEGO_DB_PATH` в изолированном каталоге на A и запустите сервер. Это восстанавливает исходное состояние без удаления старой БД. Действующий стенд и main не затрагиваются.
