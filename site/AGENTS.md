# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Durable product direction

- The separate «Рейтинг» workspace uses a compact left panel on the persistent map, with an explicit full-screen toggle. Engineer selection focuses the confirmed start point and route; its larger rounded review card is anchored at the bottom-right, aligned with the navigation/panel bottoms and clear of map controls. Explain scoring through an information popover; review entries open for reading. No «Лидерборд» label or calendar in the card.

- Latest dispatcher feedback: «Рейтинг» must reuse the Engineers panel typography, rounded tabs, search and filter sizing. Hide reserve/staff filter controls and plan composition summaries; keep only the rating plan rows and the map-level «Пересчитать план» action. Use BeeGo custom dropdowns instead of native blue selects, keep «Отзывы и разборы» actions readable, make «Показать ещё» the last sidebar navigation item after notifications, and close Rating to a neutral map without activating Orders. Use a restrained selection of high-quality non-identifying portraits and initials for the rest of the roster.

- Next planning direction: on dates without order points, the Rating plan must show the ranked engineer roster with a clear no-orders explanation instead of the generic import empty state. The next operational phase must make «Начинать смену из дома» real in the route input and expose an emergency event that preserves an in-progress visit, then reroutes from the engineer's current position after the visit finishes.
- «Отзывы и разбор» is a full-screen conversation workspace with the customer review pinned above the engineer chat, persistent messages and attachments, and a «Принять решение» form requiring an outcome and reason. Preserve original reviews and an audit trail; a dispatcher exclusion must never masquerade as a customer changing their stars. Generated history is explicitly separate from operational visit facts.
- «План по рейтингу» must reuse the existing Orders panel, route rows, search and filters. Its calculations, inputs and saved versions are independent of the normal shift. Preserve all eligibility, stock, time and road checks; do not minimize fleet size in the rating selection. Secondary navigation expands via «Показать ещё» inside a scrollable navigation area; profile/help controls remain fixed.

- Reproduce the clear GeoFlow-style navigation and split map/list hierarchy while keeping the BeeGo! planning workflow. The primary map workspace deliberately has no bottom route timeline: route details live inside expandable brigade rows and the route drawer.
- All user-facing copy must be in Russian.
- Analytics is a business decision workspace for a dispatcher, not a wall of charts. Lead with the shift outcome and no more than three actionable signals, use plain-language explanations, and reveal route-level, comparison, and validation details through separate views. Never show a metric without its operational meaning or next action.
- Analytics must offer a global cluster filter: all regions, Юго-восток, Восток, and Югоцентр. A selected cluster is isolated: never present another office's engineers as a solution for its deficit. Explain every unassigned request from live skills, availability, time windows, and route data in dispatcher language; never expose backend diagnostic codes.
- The Analytics «Ресурсы» roster is calculated from the selected engineers, orders, and routes: work, travel, idle reserve, and shift utilisation must never be hard-coded. Show one route summary, skill and transport metadata, an actionable reason for reserve, and dispatcher actions only when supported by the current regional data.
- Reserve timelines need clear, high-contrast time ticks and actionable long-wait badges. When a next visit can move earlier, expose the dispatcher action «Согласовать сдвиг окна». The dedicated «Перепланирование» view compares a live scenario before/after, route diff, decision rationale, and downstream SLA risk without hard-coded figures.
- Do not label the product interface as a demo or call its displayed data synthetic. Historical analytics must be data-driven rather than keyed to a specific dataset hash or fixed benchmark figures. The bundled historical fixture ends on the date carried by its source orders, not on the computer's wall-clock date; expose the anchor date as a generator parameter for presentation changes.
- Replace Routific's blue accent with the mascots' bright saturated yellow (`#FFD21F`); avoid dull mustard and beige accents, using clean pale-yellow tints only for larger backgrounds while preserving dark, accessible text contrast.
- The prototype must demonstrate empty state -> CSV mapping -> imported orders on a map -> route optimization -> scheduled timeline, plus representative customers, engineers, analytics, templates, and settings screens.
- Use a keyless open mapping stack for the hackathon prototype: Leaflet with properly attributed OpenStreetMap tiles; do not depend on 2GIS or Yandex APIs.
- The product name is BeeGo!. Its primary brand mark is the generated flat black-and-yellow running bee-ball, paired with a live HTML text wordmark (never rasterized). It returns users to the main map workspace when clicked and has a compact running motion on hover, with reduced-motion support.
- Keep the primary desktop navigation expanded by default with readable icons and labels, similar to GeoPotok; collapse it only when the user chooses to.
- The map should use keyless OpenStreetMap tiles with a heavily simplified pale treatment and a right-side control stack for zoom in, zoom out, fit-to-content, and map tooltip toggling. Empty-state map actions return to Moscow. Keep zoom practical (country overview through building/street level) and defer tile requests while rapid zooming for faster loading.
- Do not show trial-period or upgrade upsell UI in the hackathon prototype.
- Keep the day map theme vivid and high-contrast: fresh blue water, clearly green vegetation, warm orange roads, and readable labels.
- Support right-mouse map rotation, with a compass action in the middle map-control group that restores north-up orientation.
- Map-theme choices must use lightweight real map imagery in their previews, not generic icon placeholders; the layers button toggles its popup open and closed.
- Keep right-mouse rotation deliberately slower than MapLibre's default, and frame theme-preview imagery tightly around Moscow; the night preview must visibly use blue roads.
- Right-mouse rotation must keep a consistent drag direction during long gestures. The compass needle follows the real bearing and resets north to the top without disabling 3D.
- Use a straight, two-part north/south compass needle rather than a diagonally drawn generic compass icon.
- Empty states use separate transparent flat 2D mascot illustrations, with exactly one bee or robot per scene in black, yellow, and white line art. Never use 3D mascots or place empty-state illustrations over the map.
- Keep collapsed-sidebar icons at a clearly readable 22–23 px size, and show branded text tooltips for icon-only navigation and map controls on hover or keyboard focus.
- Sidebar expansion and collapse must keep the live map visible throughout; debounce map resizing until the width transition settles, and render collapsed active navigation as a centered, even rounded square without a detached side marker.

- Treat the sidebar identity block as the user profile: show a clear “Профиль” label, persist display name, role, email, and the chosen built-in mascot avatar locally. Roles are dispatcher, administrator, and engineer, shown through a custom BeeGo!-styled dropdown rather than a native browser select.
