# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Durable product direction

- Reserve guidance belongs inside Analytics → Resources, close to the existing “Отпустить со смены” action, without a separate prominent screen. Warn when a brigade appears important to keep on duty and show the concrete zone/skill/time reason; distinguish a heuristic recommendation from exact emergency-replanning proof.
- Write reserve-release reasons in plain Russian using the selected day's actual plan, shift times, skills, zones, and named alternative brigades when available. Do not use opaque planning terms or fixed brigade-specific explanations.

- Reproduce the clear GeoFlow-style navigation and split map/list hierarchy while keeping the BeeGo! planning workflow. The primary map workspace deliberately has no bottom route timeline: route details live inside expandable brigade rows and the route drawer.
- All user-facing copy must be in Russian.
- Replace Routific's blue accent with the mascots' bright saturated yellow (`#FFD21F`); avoid dull mustard and beige accents, using clean pale-yellow tints only for larger backgrounds while preserving dark, accessible text contrast.
- The prototype must demonstrate empty state -> CSV mapping -> imported orders on a map -> route optimization -> scheduled timeline, plus representative customers, engineers, analytics, templates, and settings screens.
- Use a keyless open mapping stack for the hackathon prototype: Leaflet with properly attributed OpenStreetMap tiles; do not depend on 2GIS or Yandex APIs.
- The product name is BeeGo!. Its primary brand mark is the generated flat black-and-yellow running bee-ball, paired with a live HTML text wordmark (never rasterized). It returns users to the main map workspace when clicked and has a compact running motion on hover, with reduced-motion support.
- Keep the primary desktop navigation expanded by default with readable icons and labels, similar to GeoPotok; collapse it only when the user chooses to.
- The map should use keyless OpenStreetMap tiles with a heavily simplified pale treatment and a right-side control stack for zoom in, zoom out, fit-to-content, and map tooltip toggling. Empty-state map actions return to Moscow. Keep zoom practical (country overview through building/street level) and defer tile requests while rapid zooming for faster loading.
- Do not show trial-period or upgrade upsell UI in the hackathon prototype.
- Keep the day map theme vivid and high-contrast: fresh blue water, clearly green vegetation, warm orange roads, and readable labels.
- Support right-mouse map rotation, with a compass action in the middle map-control group that restores north-up orientation.
- Map-theme choices must use lightweight real map imagery in their previews, not generic icon placeholders; the layers button toggles its popup open and closed. Keep this catalogue anchored to the real viewport below and to the left of the layers button, opening inward and never clipping beyond the right edge of the screen even while the application shell is rendered at 90% scale.
- Keep right-mouse rotation deliberately slower than MapLibre's default, and frame theme-preview imagery tightly around Moscow; the night preview must visibly use blue roads.
- Right-mouse rotation must keep a consistent drag direction during long gestures. The compass needle follows the real bearing and resets north to the top without disabling 3D.
- Use a straight, two-part north/south compass needle rather than a diagonally drawn generic compass icon.
- Empty states use separate transparent flat 2D mascot illustrations, with exactly one bee or robot per scene in black, yellow, and white line art. Never use 3D mascots or place empty-state illustrations over the map.
- Keep collapsed-sidebar icons at a clearly readable 22–23 px size, and show branded text tooltips for icon-only navigation and map controls on hover or keyboard focus.
- Sidebar expansion and collapse must keep the live map visible throughout; debounce map resizing until the width transition settles, and render collapsed active navigation as a centered, even rounded square without a detached side marker.
- Keep sidebar labels mounted during collapse and animate their width and opacity so navigation icons remain on one fixed axis. Keep the map's internal canvas at a stable viewport-anchored width while the sidebar animates, revealing or clipping only its left edge rather than resizing, blinking, or moving the camera.
- Support a persistent premium dark interface built from charcoal surfaces, restrained borders, warm off-white text, and saturated yellow accents. Switching to the dark interface must immediately set the map to its blue-road night theme; returning to light mode restores the vivid day map.
- Treat the sidebar identity block as the user profile: show a clear “Профиль” label, persist display name, role, email, and the chosen built-in mascot avatar locally. Roles are dispatcher, administrator, and engineer, shown through a custom BeeGo!-styled dropdown rather than a native browser select.
- The profile avatar gallery contains 16 generated transparent flat mascots in the established black, yellow, and white 2D style: four original static portraits, eight action scenes, and four additional static characters. Users choose from the built-in collection; avatar uploads are intentionally unavailable.
- A brief hover over any part of the BeeGo! wordmark must trigger the complete bee-running animation; leaving the logo before the animation ends must not interrupt it.
- The sidebar Help action opens a compact, non-blocking support center near the lower-right corner, shifted left from the map's right-side controls. The help window stays on the foreground UI layer while the zoom and map controls remain behind it. Its durable information architecture is four Russian-language tabs: Home, Training, News, and Help. Keep it consistent with BeeGo!'s yellow/charcoal visual system and structure its placeholder content so real guides, news, search, and help articles can be connected later without redesigning the shell.
- Treat the dispatcher as the primary product user. The planning workspace must support manual reassignment, protect manual overrides from later optimization, and clearly separate automatic recommendations from dispatcher decisions.
- Model each region as an independent scenario with its own office/depot, engineers, orders, and plan. One brigade is one engineer; skills, transport, and equipment are independent constraints.
- Locations are created dynamically from real imported rows. Never preload a fake city catalog: derive each city from explicit city/locality fields or the structured address, keep its orders, engineers, map camera, analytics, and plan isolated, and show only a single empty Moscow workspace before any data is loaded.
- The location selector is a dedicated top-level workspace, never a popover layered over Objects, Analytics, or another full-screen section. City cards contain only a large original city illustration, the large city name, and a concise data-loaded/empty state; do not show street addresses, city codes, or count badges there.
- New valid uploaded datasets must be plannable without first generating a sealed demo artifact. Preserve the exact canonical plan for its verified fixture, and use the validated constraint-aware planning path for arbitrary imported cities.
- The Orders and Engineers workspaces share one persistent live map instance. Switching between those panels may replace marker layers, but must never recreate, reload, recenter, re-zoom, or reset the user's bearing, pitch, theme, or map position.
- Geocoding for the prototype must stay on a genuinely free tier. Prefer a replaceable provider adapter with cached results; never invent coordinates when an address has not been geocoded.
- Show geocoding progress as a compact BeeGo!-styled notice at the map's upper-right, immediately left of the layers control. Apply each completed batch to the map incrementally, preserve successful results across transient failures, retry safely within the provider's free rate limit, and never replace progress with a raw bottom-corner browser-style toast.
- Geocode imports with structured city, street, house, building, and structure fields rather than sending the source abbreviation string as an unrestricted text search. Use each imported city as the locality and bias, put a marker on the map only when the returned house number and locality match the request, keep street-centroid guesses and mismatched buildings off the map, and report their counts explicitly.
- Keep a visible manual-resolution queue with concise structured reasons for every unassigned order, plus an estimate of the additional engineers required to complete the day.
- Emergency orders have the highest priority, may displace normal work, and should trigger a demonstrable same-day replanning flow.
- Client time windows constrain arrival and work start, not necessarily work completion. Show the client window separately from planned arrival, start, and finish.
- Keep the frontend connected only to the exact planning contracts `/api/plan` and `/api/replan`. Never publish mock, heuristic, or fallback plans; return an explicit error when exact routing or validation is unavailable.
- Settings should be a polished operational control center covering company details, independent regions and depots, planning rules, work-duration norms, import schema, and integration readiness.
- Data import is a full-screen dispatcher workspace, not a compact modal: keep the source headers and rows visible together, make cells editable, and let the dispatcher map every source column to a BeeGo! field or create a custom field before upload.
- Accept real CSV and JSON as mandatory task formats, plus XLSX and XLS as convenience formats, up to 20 MB. JSON may be an array or an object containing request collections (`jobs`, `orders`, `requests`) and engineer collections (`engineers`, `technicians`, `workers`). XLSX uses the first «Заявки» sheet and the second «Инженеры» sheet. Automatically recognize both schemas where possible, clearly identify required planning fields, and block submission until every included dataset passes validation.
- Keep a real downloadable BeeGo! workbook template aligned with the hackathon schemas: requests on the first sheet, engineers and their skills on the second, explanations on the third. CSV files without sheets can be uploaded separately from the requests and engineers screens. Never present a demo-dataset button as the primary import action; the primary action chooses or drops the user's file.
- Cancelling an in-progress import must require explicit confirmation because mapping choices and cell edits are discarded. Use smooth, reduced-motion-aware transitions and yellow robot feedback on upload-area hover or drag-over.
- Keep order markers compact at city scale and grow them progressively with map zoom. Clicking either a list row or marker must smoothly focus the exact geocoded point and open a compact Help-style detail card with the operational fields needed by a dispatcher. Clicking the same marker again closes its open detail card; clicking another marker replaces it.
- Render the shared brigade depot as a distinct circular warehouse marker, not a letter tile. Its information opens in an anchored map card beside the point (never as a detached corner panel), includes address, operating window, and participating brigades, and centers the depot without forcing a close zoom.
- Use the selected first generated yellow-roof/purple-outline circular house image (`public/depot-marker-purple.png`) for every brigade start location. Preserve its transparent exterior and do not add a separate “СТАРТ” tag below it.
- Keep every request at its real coordinates. At city scale, group nearby requests into compact aggregate clusters; expand them into individual markers by district/street scale. Requests with exactly identical coordinates receive a small deterministic screen offset so none are hidden. Refit the map when switching between assigned and unassigned requests so Orders totals never appear to disagree with the map.
- Encode the order's work type consistently in both the map marker and list bullet: emergency is red, connection is yellow, service/repair is blue, equipment work is violet, and uncategorized work is green. Keep an unobtrusive map legend visible when relevant.
- Treat imported Moscow districts and table-defined zones (`zone_name`/`zone_id`) as operational scenarios. The territory control filters both the list and the map and keeps zones and real districts in separate menu sections. Accept only real administrative OpenStreetMap/Nominatim polygons that contain a majority of the selected category's points. If a zone is arbitrary (for example «Югоцентр») or a returned polygon does not match the points, draw no area and fit the camera to every point in that category instead; never approximate a district with a circle or bounding box.
- Keep the Orders territory catalogue comfortably readable at the same type scale as the assigned/unassigned controls. On desktop it opens as a wide flyout to the right of the Orders panel, aligned with the panel's top edge, so it does not cover the request rows; fall back below the trigger only when the viewport cannot fit the side flyout.
- Present territory selection as an explicit “Выбор территории” action that always names the current selection. Its desktop catalogue opens and closes with a reduced-motion-aware sideways transition, stays to the right of Orders, and aligns its top edge with the operational panel rather than looking like a native dropdown.
- Use the bundled Moscow territory catalog first (12 administrative districts and 146 municipal territories); use Nominatim only as a fallback for Moscow Oblast or unknown real administrative areas. Keep source territory names intact and resolve aliases through `src/territoryAliases.js`.
- Reserve red map points for explicitly emergency jobs. Equipment and required skills must never make an ordinary, informational, connection, or convergence job red.
- Keep the primary map header visually empty except for a floating date control. Search, undo, download, and notification actions do not belong in the map toolbar; planning appears beside the Orders panel, while the scripted emergency action remains hidden until its final workflow is designed.
- Notifications are a first-class item in the left navigation near the operational sections. Opening them reveals a polished full-height side panel with contextual event icons, unread/all filters, and a dedicated illustrated empty state; preserve its unread badge and light/dark treatment.
- Keep the planned-brigade list collapsed by default. Each GeoFlow-style row shows only brigade name, total route time, distance, and task count; expansion reveals route statistics, stops, and a route-detail action. Treat it as a single-open accordion: opening another brigade always collapses the previously expanded route so the rest of the brigade list stays visible.
- Planned map points must remain minimalist but clearly legible: use centred circular markers that are larger than the previous micro-pins, preserve work-type colors, and scale them progressively with zoom without overwhelming a city-wide view.
- Use the approved contour-marker concept for planned requests: a warm-white centre and a 3 px outline carrying the current gray overview or selected-route accent. Show route-order numbers only for the selected brigade and only at a useful district/street zoom. Keep omitted/unassigned requests as warm-white circles with an orange dashed outline; red is reserved for emergencies and invalid data.
- Before a brigade is selected, keep all planned routes thin gray with a light casing and render every assigned request marker in the same calm neutral-gray family. Only the selected or road-hovered brigade's route becomes vivid deep purple with a thin yellow casing; its numbered request markers use the purple/yellow focus treatment while every other route and marker stays muted. This hierarchy must work in both map themes.
- Route preview belongs to a deliberate three-second road hover state, never point hover. Hovering a point may visually cross-highlight its list row but must never open a popup or route. Only clicking a point opens that request's information without selecting its route; the point card provides the secondary “Показать маршрут бригады” action. Clicking empty map space clears route focus immediately and restores the gray overview. Do not require a separate cancel-selection action.
- Fit the camera to a brigade only when that brigade first becomes active. Clicking its stops, opening request information, or changing map zoom afterwards must preserve the dispatcher's chosen camera rather than refitting the whole route.
- Operational UI accents use purple, yellow, burgundy, orange, and emergency red; do not use green for brigade avatars, assigned labels, hover states, or success emphasis. Assigned status and brigade UI are yellow; purple is reserved for map-route focus and selected point centres.
- Selecting a brigade must fit the camera to that brigade's route geometry and start point only, even though the other routes remain visible as gray context. Keep the selected route centered in the usable map area and cap the zoom so the camera never dives uncomfortably close to an individual stop.
- Orders omitted from the current plan remain visible as orange dashed contour markers. Planned request markers show their route-order number only while their route is selected; city-scale aggregate clusters show counts without pretending those counts are route sequence numbers.
- Keep the interface at its approved 90% visual scale without bottom gaps; the map controls stay visible and the date control remains centered in the viewport independently of open panels.
- Align the Locations search and city cards to exactly the same left and right edges, including when their shared list scrolls.
- In dark mode, Analytics, Planning, and Constraints use the same opaque charcoal surface as the sidebar (#1d2025). The planning/constraints content wrapper must not introduce a different rectangular background or inset shadow.
- Preserve the approved current animations: Planning, Constraints, and Locations use workspace-panel entrance/exit keyframes (300/280 ms), with a keyed outgoing/incoming transition. Do not extend this change to the other tabs without a new request; the user explicitly cancelled that expansion.
- Keep the Orders and Engineers panel headers on the same 64 px title row. Orders status filters belong on their own row below the divider, while the planning action appears on the map beside a populated Orders panel instead of competing with the panel title.
- Place the planning action in the map's upper-right corner immediately to the left of the layers/theme control. Orders and Engineers lists use a larger operational type scale. Selecting an engineer opens an animated, full-height, scrollable detail card immediately to the right of the Engineers panel at the same top level; it shows imported availability, shift, transport, territory, route and stops, start point, skills, equipment, and contacts. Never infer availability when the imported status is missing. The Engineers list shows all skills, transport, and today's planned route/stop counts, with search and filters for no route or 1–3 stops once a plan exists. Orders also has a visible list search.
- Orders status pills keep the same dimensions and typography as Notification tabs, but use a restrained pale-yellow selected state with a yellow outline rather than a solid bright-yellow fill.
- Header icon tooltips in Orders and Engineers must stay fully readable on hover: right-align them within the panel and keep the header above the status/filter row so neither panel clipping nor adjacent controls cover their text.
- In Orders, keep the title row limited to its title/count and close control. The file-upload action uses an upward file icon at the right edge of the filter row; the scripted emergency-test button stays hidden until a real emergency workflow is designed. Keep its tooltip readable above the following content.
- Map markers must remain inside the map stacking context; no marker may paint above route, engineer, policy, notification, or other interface panels.
- In dark Notifications, every notification illustration uses the same warm light artwork tile as “Данные успешно загружены”; notification type changes the artwork, not its tile background.
- In dark Planning, replanning slider labels change text color on hover without drawing a rectangular hover background.
- Import mapping profiles each column from its values and offers compatible unused fields first (number, text, boolean, time, date, email, phone, or list), with an explicit full-list override. Unknown source columns are preserved as custom fields rather than left red and unmapped.
- Import review has bounded undo/redo history for field mappings and cell edits, exposed as toolbar buttons and Ctrl+Z/Ctrl+Y shortcuts.
- Name the full-screen import review tab and page “Данные”. Keep both status filters visible in Orders from the start with “Назначены” on the left and “Не назначены” on the right; disable both until a route plan exists and enable them after a successful plan. The Data header includes a compact source-file button in the existing controls area; its popup lists previously reviewed files and offers separate add-file actions for requests and engineers without displacing the dataset tabs, and always paints above the sticky table header. Map point cards open on click, include readable medium-weight operational details, and paint above map markers. Omitted-order red markers stay on the regular map marker layer. Focusing a point should center it in the visible map area without zooming past neighborhood scale automatically.
- Keep import review's source-column filters in the source-header row, with the same dropdown language as field mapping. Both menus must align to the clicked column even under the app's 90% CSS zoom. In the light theme the mapping menu header is white and its “Назначение столбца” title is prominent. The review table owns the full width; only compact validation counts remain in the toolbar immediately before undo/redo. Use a transparent BeeGo! illustration instead of a document icon beside “Данные”. Its close icon has no resting border or tile and uses the same gray rounded hover treatment as the Notifications close icon; its hit area is slightly taller than the adjacent dataset tabs, not smaller.
- After a successful upload, keep the latest reviewed source table, column mappings, and edits for each data type in the active session, available through a dedicated “Данные” navigation item. Reopen the same full-screen editor, allow changes to be saved back through the existing import pipeline, and retain the confirmation dialog for discarding unsaved edits. Its “Вернуться к таблице” button uses a clearly visible gray hover/focus state, not yellow.
