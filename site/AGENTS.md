# Prototype Instructions

- Rating staffing uses the selected shift's stored engineer profiles and validated historical membership, not the later roster seed date or another day's shifts. Normalize retained territory/equipment formatting without rewriting published inputs. Preserve rating bounds, explicit unavailability and current/future roster periods; never adapt reserve home origins or shifts just to make them eligible.

- Preserve access to retained historical operational days in Orders, Engineers and Shift through the shared date selector. Load saved independently validated orders, crews and road geometry from the full history archive; never generate replacement history or fabricate completion facts from analytics summaries. Preserve existing shift revisions and dispatch sessions when restoring missing days.

- Engineer comments are short natural first-person explanations of why a visit was faster or slower, suited to the actual work and recorded context. Never append archive IDs, plan/actual reports, work/paperwork minute breakdowns, or model-review language to their messages. Show plan versus actual as the whole visit in the feedback card. Keep repeatability and future-transfer decisions in the separate operator/system controls. Correct only untouched synthetic fixture prose; retain human replies, measured facts, model inputs and published calculations.

- Put engineer feedback immediately below the duration formula in the passport overview. Show measured plan/actual differences, the engineer's explanation, review state, scope, future affected orders, retained calculations and every reply/decision version. Keep one common passport scroll and reveal full lists explicitly. Preserve unsaved reply drafts when switching passport tabs. Remove the extra full-width map extent button from the time panel; keep the existing map controls.
- Engineer explanations are evidence, never direct minute overrides. New feedback transfers require at least four comparable measured visits, multiple days and two engineers, robust residuals after work-volume factors, chronological holdout improvement and no deterioration versus saved adaptive forecasts. Never broaden one line's evidence to a whole house; shared operations require several houses. Client waiting is a separate stage, scoped only to an explicitly linked account. Keep zero distinct from unknown, exclude manual/erroneous measurements, honour expiry/closure and stop applying new feedback policies when later evidence contradicts them. Seed engineer messages separately without rewriting archived measurements, snapshots or published plans.

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

Do not substitute a different engineer silently. Retain compact server-issued selection receipts across candidate refreshes and wait for a busy planner during confirmation. Show errors once; a genuinely failed confirmation waits for an explicit operator retry instead of restarting generic search automatically. Show the published result prominently and collapse other alternatives; restore the previous speed only after successful acceptance, preserving pause and other pending incidents. Delayed temporary-clock requests must not reset the restored speed or rewind time.
- Keep the playback bar free of the «Ожидаем решения» badge; retain the actual ×1 speed and incident decision controls. A newly received pending emergency immediately gets a red map marker and one camera focus, and automatically opens the left emergency tab once on arrival. Retain an incident focus sent before map attachment, retry it after style loading, and render the emergency marker from candidate coordinates when previewing a route. Polling must not refocus an already announced incident.
- Camera padding is expressed in MapLibre's internal clientWidth/clientHeight pixels. Convert every screen DOM rectangle and marker extent back through the measured horizontal/vertical scale, including the app's 90% zoom; never use DPR-scaled canvas bitmap dimensions. Reserve both horizontal halves of the actual visible stop/address labels and their wrapped height, using shared label dimensions with the renderer.
- Notification opening and acknowledgement use a shared flex action row with full labels, including the read state; never overlap them with absolute positioning. Emergency camera framing measures actual panel, map controls and timeline rectangles and preserves engineer/emergency anchors in both route scopes, including after resizing and panel animations. Playback displays the actual speed, including ×1; the decision-wait status belongs in the incident panel, not the playback bar. The server owns temporary slowdown and restores the saved speed only when the whole pending queue is resolved, preserving the current pause state for manual and automatic decisions. Client writes are serialized and old poll versions cannot restore a stale clock or incident state.
- Early arrival followed by waiting until the client window opens is allowed: flag early work start or arrival/start after the closing boundary, never early arrival alone. After a decision is accepted, only that exact candidate uses applied wording; other alternatives remain prospective and explicitly unaccepted. Keep compact per-candidate coverage («Аварии N/N · всего N/N»), counting emergency work separately from ordinary urgent jobs.

Explain recommendations with measured coverage/reserve/arrival differences against an actual available alternative. Keep the chosen engineer, ETA, main consequence, countdown and «Направить на аварию» together in the sticky bar. Use one inline route key; remove repeated instructional blocks and floating duplicate legends. Consequence groups reveal addresses with map actions. After publication, show the dispatched engineer and transfer recipients, apply the new plan immediately, and show only the normal purple/red selected-route comparison. Do not add a yellow route overlay or a «Подсветить изменённые маршруты» action, including automatically after confirmation.

Search and independent replay share the same fact interpretation. After acceptance, every emergency comparison uses the candidate's saved base revision, including affected engineers; never replace the original plan with the current published plan. Reject a missing or checksum-mismatched base explicitly.
- Preserve factual job protection, engineer release times and locked routes through departure timing and final validation. Rebase older pending incidents after any publication. Refresh future duration snapshots from the active model/history while preserving departed and fact-started work. Unknown release of one engineer locks only that engineer; never block the remaining team. Keep confirmation and the route color key visible in a sticky panel bar; on narrow screens use the inline key instead of an overlapping floating legend. Missing experience and customer ratings must be labelled as missing archive data, never fabricated.
