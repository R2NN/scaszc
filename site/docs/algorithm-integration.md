# Интеграция алгоритма маршрутизации BeeGo!

## Что подключено

Интерфейс BeeGo! использует опубликованные артефакты из `algorithm/artifacts/current/`. Основной план построен Python-ядром на OR-Tools CP-SAT с временами и геометриями Valhalla. Отдельный FCFS-план рассчитан тем же точным маршрутизатором и проверен тем же независимым валидатором.

В браузер публикуется только результат, который одновременно удовлетворяет трём условиям:

- `status = EXACT_VALID`;
- `publication_allowed = true`;
- `validation.status = VALID`.

Worker дополнительно сверяет полный набор исходных ID заявок и наличие всех инженеров, задействованных в плане. Если данные изменены, неполны или относятся к другому набору, API возвращает `422 UNSEALED_DATASET` и не создаёт выдуманный маршрут.

## Поток данных

`импорт заявок и инженеров → сопоставление полей → координаты → /api/plan → проверка контрольных сумм и статуса → назначения и геометрии маршрутов → карта и карточки`

Файл `public/data/beego-exact-plans.json` содержит компактное представление трёх проверенных артефактов:

- исходный сценарий: 205 заявок, 205 назначено, 28 активных маршрутов;
- сценарий события: 206 заявок, 206 назначено, 28 активных маршрутов;
- точный FCFS-бейзлайн: тот же набор 205 заявок, те же Valhalla/транспортные маршруты, ограничения и валидатор; 104 назначения, 35 бригад, 1 069,5 км.

Время выезда теперь подбирается в Python-конвейере после построения допустимого плана. Для слишком раннего приезда алгоритм пробует отправить инженера позже и **заново запрашивает маршрут на эту минуту**. Цель — приехать не раньше чем за 15 минут до начала работы. Если новый маршрут не успевает, недоступен или нарушает ограничение, остаётся исходный проверенный выезд. После подстройки валидатор проверяет весь план. После события уже начатые поездки не меняются, а план события строится от опубликованного исходного плана.

На текущем дне это изменило 27 переездов: суммарное ожидание непосредственно у клиента сократилось с 2 562 до 506 минут, максимальное — с 251 до 31 минуты. Назначения и времена начала работ сохранены, исходный план остаётся 205/205, событийный — 206/206. Ожидание до выезда остаётся частью смены и не скрывается из общего учёта времени.

Для исходной смены это даёт проверяемое сравнение: оптимизатор выполняет на 101 заявку больше, задействует на 7 бригад меньше и сокращает средний пробег на визит на 22,4%. Суммарный пробег двух планов нельзя сравнивать без учёта разницы в объёме работ.

Для интерфейсной проверки создан объединённый файл `public/test-data/beego-algorithm-integration.json`: в нём 206 заявок и полный список инженеров с навыками, транспортом, оборудованием, сменами и стартовыми точками.

Файл `public/test-data/beego-algorithm-initial.json` содержит исходные 205 заявок. Кнопка «Новая авария» добавляет каноническую заявку `EAST-EVENT-001` и переключает интерфейс на проверенный событийный план.

## Воспроизводимость

Опубликованные артефакты можно преобразовать заново командами:

```powershell
pnpm run build:planning-artifact
pnpm run build:analytics-history
```

Скрипт отклоняет основной, событийный или FCFS-артефакт без точного валидного статуса. Для полного перерасчёта нового произвольного набора требуются запущенная Valhalla и заново построенные маршруты; команда воспроизведения FCFS приведена в `algorithm/BENCHMARK_2026-09-22.md`.

## Важное ограничение перед демонстрацией

Текущая web-интеграция публикует два проверенных сценария оптимизатора; FCFS используется для сравнения исходной смены в аналитике. Произвольно изменённый набор нужно сначала прогнать полным Python-конвейером с Valhalla и валидатором. Для синтетических исторических дат без точного FCFS интерфейс не показывает сравнительные километры и рубли.

В текущем рабочем каталоге лежат `data/screening/`, транспортный индекс и кэш точных маршрутов. Поисковые матрицы служат для оптимизатора предварительной оценкой и не используются FCFS как доказательство недопустимости кандидата.

## Результат проверки

- `pnpm run test:algorithm`: оба сценария оптимизатора и FCFS имеют `EXACT_VALID`; у назначений есть дорожная геометрия либо подтверждённый нулевой переход между заявками по одному адресу, 101 неназначенная FCFS-заявка сохранена явно;
- `pnpm run test:analytics-history`: 43 проверки аналитики и FCFS пройдены;
- `pnpm run test:sites`: 14 проверок Worker/API пройдены;
- `pnpm run build`: production-сборка успешна;
- контрольные данные: исходный план 205/205 на 28 бригадах, событийный 206/206 на 28, FCFS 104/205 на 35;
- `algorithm/tests/test_baseline.py`: обе проверки правил FCFS и общего оборудования пройдены.

Точный FCFS-артефакт имеет `EXACT_VALID`, независимый `VALID` и `publication_allowed: true`; веб-экспорт дополнительно проверяет полное покрытие исходных ID назначениями и списком неназначенных.
