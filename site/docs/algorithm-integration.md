# Интеграция алгоритма маршрутизации BeeGo!

## Что подключено

Интерфейс BeeGo! использует точные планы из пакета `LCT2_ALGORITHM_UI_HANDOFF_FINAL_2026-09-17.zip`. План построен Python-ядром на OR-Tools CP-SAT с дорожными временами и геометриями Valhalla.

В браузер публикуется только результат, который одновременно удовлетворяет трём условиям:

- `status = EXACT_VALID`;
- `publication_allowed = true`;
- `validation.status = VALID`.

Worker дополнительно сверяет полный набор исходных ID заявок и наличие всех инженеров, задействованных в плане. Если данные изменены, неполны или относятся к другому набору, API возвращает `422 UNSEALED_DATASET` и не создаёт выдуманный маршрут.

## Поток данных

`импорт заявок и инженеров → сопоставление полей → координаты → /api/plan → проверка контрольных сумм и статуса → назначения и геометрии маршрутов → карта и карточки`

Файл `public/data/beego-exact-plans.json` содержит компактное представление двух проверенных артефактов:

- исходный сценарий: 205 заявок, 204 назначено, 1 не назначена, 31 активный маршрут;
- сценарий события: 206 заявок, 205 назначено, 1 не назначена, 32 активных маршрута.

Для интерфейсной проверки создан объединённый файл `public/test-data/beego-algorithm-integration.json`: в нём 206 заявок и полный список инженеров с навыками, транспортом, оборудованием, сменами и стартовыми точками.

Файл `public/test-data/beego-algorithm-initial.json` содержит исходные 205 заявок. Кнопка «Новая авария» добавляет каноническую заявку `EAST-EVENT-001` и переключает интерфейс на проверенный событийный план.

## Воспроизводимость

Извлечённый handoff-пакет можно преобразовать заново командой:

```powershell
npm run build:planning-artifact
```

Скрипт отклоняет артефакт без точного валидного статуса. Сам Python-пакет устанавливается из `src/` handoff-пакета и использует OR-Tools. Для полного перерасчёта нового произвольного набора требуются запущенная Valhalla и заново построенные матрицы/геометрии.

## Важное ограничение перед демонстрацией

Текущая web-интеграция гарантированно публикует два подписанных сценария из handoff-пакета. Произвольно изменённый набор намеренно не оптимизируется в браузерном Worker: его сначала нужно прогнать полным Python-конвейером с Valhalla, проверить валидатором и только затем публиковать. Это защита от правдоподобных, но неверных маршрутов.

В переданном архиве отсутствует каталог `work/routing/screening`, на который ссылается часть тестов воспроизводимости. Поэтому готовые точные артефакты проходят проверку контрольных сумм, а полный свежий прогон из одного архива требует регенерации этих матриц.

## Результат проверки

- `npm run test:algorithm`: оба сценария `EXACT_VALID`; у назначений есть дорожная геометрия либо подтверждённый нулевой переход между заявками по одному адресу, а единственная неназначенная заявка явно сохранена в результате;
- `npm run test:sites`: 8 из 8 проверок Worker/API пройдены;
- `npm run build`: production-сборка успешна;
- браузерный сценарий: импорт 205 заявок и 35 инженеров → 204 назначения и 1 неназначенная → контрольная авария → 205 назначений и 1 неназначенная;
- карта после событийного расчёта получает 205 подтверждённых назначений.

Внутренние тесты самого переданного Python-пакета дали 89 успешно пройденных и 2 пропущенных теста. Ещё 3 проверки завершились ошибкой утверждения и 5 не запустились из-за отсутствующих в архиве файлов `work/routing/screening/*` и ожидаемого тестами файла `normatives-exact-improved.json`. Оба фактически переданных explained-артефакта отдельно прошли проверку формата и контрольных сумм.
