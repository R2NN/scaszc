# Стенд BeeGo! на одном сервере

## Рекомендуемая конфигурация

Для демонстрации с доступом нескольких зрителей и одним точным расчётом: **8 vCPU, 32 ГБ RAM, 160 ГБ NVMe SSD, Ubuntu 24.04 LTS**. Это консервативный стартовый размер, а не измеренный предел нагрузки. При показе только уже опубликованных планов хватит меньшего сервера; уменьшать мощность для новых расчётов следует после замера CPU, RSS и времени работы на выбранном наборе. GPU не нужен.

Схема: Nginx отдаёт собранный React и проксирует `/api/` к **одному** процессу Node.js. Node.js запускает Python-планировщик; Valhalla работает локально и не открывается в интернет. В этом режиме сайт могут читать одновременно многие посетители, но в любой момент выполняется только один новый расчёт или пересчёт. Второй запрос получает HTTP 429 и сообщение «Подождите: другой пользователь уже запустил расчёт…». Канонические готовые планы доступны без запуска Python. Несколько экземпляров Node.js без общего распределённого замка запускать нельзя.

## Источники и перенос данных

Git содержит исходный код, контрольные данные и проверенные демонстрационные артефакты. Полный переносимый архив `BeeGo_COMPLETE_2026-09-28.zip` хранится отдельно и **не загружается в GitHub**. Из него на сервер в `/srv/beego` нужно перенести:

- `valhalla-data/` (тайлы и конфигурация Valhalla);
- `offline-assets/transit-sources/` (GTFS, железная дорога и метро для нового дня);
- `data/transit/moscow_2026-08-17.sqlite` и одноимённые файлы `.manifest.json`, `.surface_walk_transfers.json`, `.walk_transfers.json` (проверенный индекс контрольного дня).

Иерархию каталогов сохранить. Windows Python wheels, `node_modules`, `dist`, логи и секреты переносить не нужно. Перед распаковкой проверить свободный диск: в исходном ZIP около 7 ГБ распакованных данных, включая дублированные тайлы. Сверить контрольную сумму ZIP и `PACKAGE_MANIFEST_SHA256.tsv` из исходного комплекта.

## Подготовка Ubuntu

1. Установить Node.js 20+, pnpm, Python 3.13, Docker Engine, Nginx и Git. Зафиксировать версии в журнале сдачи. Создать пользователя `beego` и каталог `/srv/beego` с правами этого пользователя.
2. Получить нужную ветку GitHub в `/srv/beego`. Перенести перечисленные офлайн-данные отдельно, без секретов. Убедиться, что `/srv/beego/runtime` доступен для записи пользователю `beego`.
3. Создать Python-окружение `/srv/beego/.venv` и установить `algorithm/requirements-full.txt` и `site/requirements-ml.txt`. В `/srv/beego/site` выполнить `pnpm install --frozen-lockfile` и `pnpm run build`.
4. Скопировать `deploy/api.env.example` в `/etc/beego/api.env`, выставить права `0600`, вписать реальные ключи Geoapify и Яндекс Расписаний только при необходимости. Не коммитить этот файл.
5. Запустить совместимый образ Valhalla 3.8.3 из переносимого архива (`docker load -i offline-assets/docker/valhalla-scripted-3.8.3.tar`) с каталогом `valhalla-data`, смонтированным как `/custom_files`. Использовать параметры контейнера из `START_BEEGO.ps1` в исходном ZIP; заменить публикацию порта на `127.0.0.1:8002:8002` и включить `--restart unless-stopped`. Проверить `curl http://127.0.0.1:8002/status` до запуска API. На Linux автоматический WSL-старт из `ensure_local_valhalla.py` недоступен, поэтому работающий endpoint Valhalla обязателен.
6. Скопировать `deploy/beego-api.service` в `/etc/systemd/system/`, выполнить `systemctl daemon-reload` и `systemctl enable --now beego-api`. Скопировать `deploy/nginx.conf` в конфигурацию Nginx, заменить `example.org` на домен, проверить `nginx -t` и перезагрузить Nginx. Настроить HTTPS сертификат для домена. Снаружи открыть только 80/443; 8787 и 8002 оставить локальными.

## Проверка перед показом

```bash
curl -fsS http://127.0.0.1:8002/status
curl -fsS http://127.0.0.1:8787/api/health
curl -I http://example.org/
curl -I http://example.org/data/beego-exact-plans.json
```

Затем открыть сайт, показать исходный план 205/205, добавить контрольную аварийную заявку и показать 206/206, изменение маршрута и сравнение с FCFS. Для проверки запрета параллельного расчёта отправить два непохожих новых набора почти одновременно: один должен запуститься, второй получить HTTP 429; после завершения первый слот должен снова освободиться. Эту проверку на реальном сервере следует провести до публичной ссылки. При отказе Valhalla или отсутствии индекса новых дат API должен вернуть ошибку, а не выдавать непроверенный маршрут.

Наблюдать `systemctl status beego-api`, `journalctl -u beego-api`, `docker logs`, свободный диск, RSS Python и длительность планирования. Сохранять резервные копии `runtime/ui-runs` и необходимых конфигураций; временные кэши можно регенерировать. Для публичного стенда ограничить доступ к запуску расчёта средствами Nginx, если ссылку планируется широко распространять.
