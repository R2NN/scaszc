# Локальный маршрутизатор для алгоритма

Рабочий провайдер CLI: `valhalla-local-transit`. Запросы маршрутов не обращаются к 2ГИС, HERE или платному API. Автомобиль, велосипед и пеший путь рассчитывает локальная Valhalla. Для общественного транспорта используются расписания наземных маршрутов, МЦК и МЦД, а также модель метро.

## Что входит в расчёт

| Транспорт | Данные | Качество времени |
| --- | --- | --- |
| Автобус, трамвай | GTFS Москвы, календарь проверен на `2026-08-17` | Время отправления и прибытия из GTFS |
| МЦК, МЦД, пригородные поезда на охваченных станциях | Замороженные ответы API Яндекс Расписаний на обычный понедельник `2026-09-21` | Реальные отправления из выбранного эталонного дня, перенесённые по времени суток на сценарный понедельник |
| Метро | Официальная схема Московского метрополитена: времена перегонов, переходов, входа и выхода, время первых и последних поездов | Оценка с явным ожиданием **180 секунд при каждой посадке** по умолчанию; полного расписания отправлений нет |
| Пешие подходы и переходы между наземными остановками | Локальная Valhalla на OSM | Время и длина пешеходного маршрута по улицам |

Дата в исходном синтетическом наборе **остаётся 17 августа 2026 года**. Эталон 21 сентября используется только для часов отправления МЦК/МЦД. Это обычный понедельник, который команда разрешила взять вместо специальных изменений расписания. Для метро не создаются вымышленные отправления поездов: ожидание является параметром модели. В JSON такой результат помечается `METRO_MODEL_WAIT_ASSUMPTION`, а его `provenance` содержит число посадок и чувствительность выбранного пути к ожиданию от 0 до 5 минут на посадку. Такой результат подходит для приближённого планирования, но не доказывает точный оптимум.

Метро участвует в общей сети: поддерживаются маршруты вида «автобус → метро → автобус», переходы метро ↔ МЦК/МЦД и чистые поездки на метро. Для короткого расстояния алгоритм также сравнивает прямой пеший путь. Поскольку ожидание метро моделируется, для планировщика всё равно нельзя заявлять доказанный глобальный оптимум по историческому расписанию.

Геометрия поездок между станциями и остановками — отрезки между точками посадки; она не является точной траекторией рельсов или улиц. `distance_m` для этих участков — геодезическая нижняя оценка. Расписание и длительность от этого не зависят. Пешая геометрия взята из Valhalla.

## Проверка и один маршрут

Работать из `A:\LCT2-routing\handoff` при запущенном контейнере `valhalla-moscow`:

```powershell
$env:PYTHONPATH = 'src'
python -m beeline_routing.cli preflight `
  --dataset work\dataset_v21\beeline_synthetic_dataset_v2_1

python -m beeline_routing.cli route `
  --dataset work\dataset_v21\beeline_synthetic_dataset_v2_1 `
  --origin-id LOC-0001 --destination-id LOC-0002 `
  --mode PUBLIC_TRANSIT `
  --departure-at 2026-08-17T09:00:00+03:00 `
  --cache work\routing\local_routes.sqlite `
  --output work\transit\example.json
```

Допущение ожидания метро хранится в самом индексе, чтобы все расчёты команды были воспроизводимыми. Изменение `--metro-wait-seconds` без пересборки отклоняется. Чувствительность уже записывается в ответ для ожидания от 0 до 5 минут на каждую посадку. Для других видов транспорта тот же CLI использует локальную Valhalla.

Маршруты берутся из готового индекса `work\transit\moscow_2026-08-17.sqlite`; ключи при расчёте **не нужны**. На проверенных парах из набора один запрос занимал около 5–10 секунд на этой машине. Для новых адресов, уже привязанных к координатам, индекс пересобирать не требуется. Пересборка понадобится при смене даты, расписаний или территории.

## Подключение к планировщику

Сначала строятся бесплатные локальные матрицы предварительного отбора. Для автомобиля, велосипеда и пешего движения используется `/sources_to_targets` той же Valhalla; отдельные пустые ячейки автоматически перепроверяются обычным локальным `/route`. Матрица общественного транспорта строится по топологии и длительностям локального индекса, калибруется по детальным маршрутам и сравнивается с прямым пешим маршрутом Valhalla:

```powershell
$env:PYTHONPATH = 'src'
python tools\build_valhalla_screening_matrices.py `
  --dataset work\dataset_v21\beeline_synthetic_dataset_v2_1 `
  --output work\routing\screening-local

python tools\build_local_transit_screening_matrix.py `
  --dataset work\dataset_v21\beeline_synthetic_dataset_v2_1 `
  --transit-index work\transit\moscow_2026-08-17.sqlite `
  --walking-screening-root work\routing\screening-local `
  --output work\routing\screening-local

python tools\solve_screening_master.py `
  --dataset work\dataset_v21\beeline_synthetic_dataset_v2_1 `
  --scenario core `
  --screening-root work\routing\screening-local `
  --output work\planning\all-local-screening-candidate.json `
  --seconds-per-tier 45 --max-predecessors 8
```

Матрица общественного транспорта остаётся поисковой оценкой. В ней нет коэффициента или временного буфера: множитель равен `1,0`, добавка равна `0`. Поэтому статическая оценка иногда недооценивает ожидание транспорта в конкретную минуту. Итоговый кандидат обязательно пересчитывается детальным маршрутизатором по порядку всего рабочего дня; несовместимые последовательности исключаются или заявка возвращается в нераспределённые.

В начальном CP-SAT сначала идёт отдельный поиск плана с нулём неназначенных заявок по полному графу
допустимых переходов. Если лимит времени исчерпан, возвращается `NO_SOLUTION_WITHIN_LIMIT`, а найденный неполный
кандидат не публикуется. Переход к частичному плану возможен только явным флагом после доказанной несовместимости.

После 100% покрытия фиксируется минимальное число бригад. Только после этого минимизируется сумма
времени реакции на назначенные аварии — от момента их появления/планирования до
начала работы. Поэтому аварии начинаются раньше, но это не может уменьшить
покрытие или потребовать дополнительную бригаду; дальнейшие уровни сокращают
расстояние, время в пути, ожидание и дисбаланс.

Длительность работы берётся из `Нормативы.xlsx` без справочных 20 минут дороги: подключение — 70 минут, глобальная проблема — 80, дозаказ — 20, локальная заявка — 30. Дорога всегда рассчитывается маршрутизатором отдельно. Время заявки — закрытое окно начала работы: специалист может начать в любой момент от начала до конца окна включительно, после чего выполняет полный норматив. Завершение допускается после конца окна, но только внутри смены.

Скрипты проверки кандидата и последовательного перерасчёта плана по умолчанию используют тот же локальный провайдер. Файл ключей для них не обязателен:

```powershell
$env:PYTHONPATH = 'src'
python tools\probe_exact_candidate.py `
  --dataset work\dataset_v21\beeline_synthetic_dataset_v2_1 `
  --scenario core `
  --master-solution work\planning\all-local-screening-candidate.json `
  --cache work\routing\local_routes.sqlite `
  --transit-index work\transit\moscow_2026-08-17.sqlite `
  --output work\planning\all-local-route-probe.json `
  --execute

python tools\materialize_exact_plan.py `
  --dataset work\dataset_v21\beeline_synthetic_dataset_v2_1 `
  --scenario core `
  --master-solution work\planning\all-local-screening-candidate.json `
  --cache work\routing\local_routes.sqlite `
  --transit-index work\transit\moscow_2026-08-17.sqlite `
  --output work\planning\all-local-materialized-plan.json `
  --execute
```

Первый скрипт проверяет достижимость участков и сохраняет контрольную точку после каждого инженера. Второй последовательно пересчитывает времена прибытия и проверяет окна работ и смены. В каждом артефакте записываются провайдер, индекс, допущение ожидания метро и признак отсутствия полного исторического расписания метро.

Текущий основной артефакт `full-coverage-exact-reordered-chain-v3-explained.json` обслуживает 204 из 205 заявок, известных в начальный момент 07:00, силами 31 инженера. Все 15 срочных заявок назначены; одна обычная заявка `SOUTHEAST-79450` осталась нераспределённой после 7 072 точных проверок локального ремонта. В исходном CORE-файле 206 строк: одна заявка создаётся позже событием и по правилам не входит в начальный план. Нарушений ограничений в опубликованных 204 назначениях нет. Статус `EXACT_VALID` означает точную проверку ограничений относительно сохранённых расписаний и принятой модели метро. Он не означает доказанный глобальный оптимум или наличие полного исторического расписания метро; это отдельно записано как `exact_historical_metro_timetable_proof: false`.

Причина неназначения записана в объяснениях результата. Для заявки есть статически подходящие специалисты, но ограниченный поиск прямых вставок, перестановок и цепочек не нашёл точного допустимого изменения. Это не доказательство глобальной невозможности при полной перестройке всех маршрутов.

### Поиск переносов и обменов

`tools/repair_exact_plan.py` продолжает точный план: пробует прямую вставку, перестановку внутри маршрута, переносы и цепочки до четырёх вытеснений. Каждый перенос ограничен `zone_id` инженера и заявки, а также навыком, транспортом и оснащением. Перспективные порядки проверяются детальным маршрутизатором; найденное изменение принимается только после повторной точной проверки **всего** плана. Исходный файл не перезаписывается, для результата требуется новый путь.

```powershell
$env:PYTHONPATH = 'src'
python tools\repair_exact_plan.py `
  --dataset work\dataset_v21\beeline_synthetic_dataset_v2_1 `
  --scenario core `
  --input-plan work\planning\normatives-exact-improved.json `
  --cache work\routing\exact-repair-search.sqlite3 `
  --transit-index work\transit\moscow_2026-08-17.sqlite `
  --output work\planning\coverage-repair-new.json `
  --max-route-checks 5000 --max-displacements 4 --max-passes 10 --execute
```

Перед запуском локальная Valhalla должна быть доступна, а файл кеша — существовать или быть созданным в рабочем каталоге. `--trust-input-validation` пропускает повторный расчёт исходного плана только при наличии проверенного контрольной суммой опубликованного артефакта; каждый изменённый план всё равно пересчитывается целиком. `search_reports` показывает затраченные проверки по глубине и по заявке. Исчерпание бюджета или отсутствие найденного хода **не доказывает** недостижимость полного покрытия.

### Перепланирование после события

`tools/replan_exact_plan.py` применяет одно следующее событие из набора к опубликованному `EXACT_VALID` плану. Повторные события запускаются последовательно, используя предыдущий результат как `--input-plan`. Поддерживаются новая срочная заявка, отмена и недоступность инженера. Все визиты, к которым инженер уже выехал к минуте события, остаются неизменными; будущие визиты перепроверяются и могут быть переназначены только внутри своего района. При недоступности начатый визит завершается, а дальнейшие выезды разрешены не раньше `unavailable_until`. Отмена начатой заявки отклоняется с `REJECTED_ALREADY_STARTED`.

```powershell
$env:PYTHONPATH = 'src'
python tools\replan_exact_plan.py `
  --dataset work\dataset_v21\beeline_synthetic_dataset_v2_1 `
  --scenario core `
  --input-plan work\planning\normatives-exact-improved.json `
  --event-id CORE-EVT-001 `
  --cache work\routing\exact-repair-search.sqlite3 `
  --transit-index work\transit\moscow_2026-08-17.sqlite `
  --output work\planning\normatives-event-001-replanned.json `
  --max-route-checks 400 `
  --urgent-slack-minutes 15 `
  --urgent-ejection-gain-minutes 45 --execute
```

Исходный план сверяется по SHA-256 и независимо валидируется; выход записывается только в **новый** файл. План публикуется лишь после независимой проверки всего рабочего дня: зон, окон, смен, навыков, транспорта, оборудования, расходников, обязательных назначений и неизменности уже начатого. Ошибка обязательного маршрута или непроверенный кандидат для оставшейся заявки дают `ROUTING_INCOMPLETE`, а не вымышленную недостижимость.

Текущий поиск — ограниченная эвристика: сначала сохраняет допустимые будущие назначения, затем пытается вставить нераспределённые и новые заявки. Срочные заявки рассматриваются раньше обычных. Среди вариантов, начинающихся не позже чем через 15 минут от самого раннего найденного старта, выбирается меньший сдвиг уже назначенных работ, затем меньше новых бригад и добавочного пробега. Если обычная вставка задерживает аварию существенно, допускается вытеснить **не более одной** будущей обычной заявки; сначала ищется новое место для неё. Порог существенного выигрыша — 45 минут при восстановлении этой заявки и 90 минут, если она останется нераспределённой. Оба значения настраиваются в CLI и записываются в `urgency_policy` результата. Начатые поездки/работы вытеснять нельзя.

`budget_exhausted` и `unserved_reasons` показывают пределы поиска. **Глобальный оптимум покрытия, времени реакции, числа бригад и пробега не доказывается.** Для сценария `stress` требуется собственный начальный план, удовлетворяющий его жёсткому предварительному назначению; исходный план `core` нельзя автоматически считать его заменой.

### Объяснение решений

Новые артефакты `materialize_exact_plan.py` и `replan_exact_plan.py` содержат раздел `explanations`. Он строится только из входных данных, сохранённых проверенных кандидатов и результата независимого валидатора; свободная языковая модель для вывода причин не используется. Для каждой заявки сохраняются:

- итоговый статус и короткое русское объяснение;
- район, навык, транспорт, оснащение, окно, смена и маршрутное подтверждение;
- назначенная бригада, время реакции, участок поездки и изменение относительно предыдущего плана;
- число статически подходящих бригад и агрегированные причины отсева остальных;
- до пяти лучших точно проверенных альтернатив для новой срочной заявки;
- уровень доказательности: точный факт, независимо проверенный результат, локальная невозможность, исчерпанный лимит поиска или непроверенный маршрут.

Фразы о глобальном оптимуме и глобальной невозможности не выводятся без соответствующего доказательства. В частности, отсутствие одиночной вставки означает только локальную невозможность вставить заявку в текущие маршруты. В интерфейсе рекомендуется сначала показывать `summary_ru` и `claim_level`, а по раскрытию — ограничения, альтернативы и `run_certificate`.

Добавить объяснения к уже опубликованному начальному плану можно без его перезаписи:

```powershell
$env:PYTHONPATH = 'src'
python tools\explain_exact_plan.py `
  --dataset work\dataset_v21\beeline_synthetic_dataset_v2_1 `
  --scenario core `
  --input-plan work\planning\normatives-exact-improved.json `
  --output work\planning\normatives-exact-improved-explained.json
```

Скрипт сначала проверяет контрольную сумму исходного файла и повторно валидирует весь план. Результат записывается только в новый путь и получает собственную контрольную сумму.

### Контрфактический запрос «почему не эта бригада»

`tools/explain_assignment_counterfactual.py` принимает произвольную пару `job_id`/`engineer_id`. Для начального плана выполняется ограниченный точный поиск прямой вставки, переноса или цепочки до двух вытеснений. Для плана после события исходное событие повторяется из зафиксированного предыдущего состояния, но выбранная заявка разрешается только указанной бригаде. Уже начатые активности не изменяются, а район, навыки, транспорт, оборудование, окна, смены и общий запас остаются жёсткими ограничениями.

```powershell
$env:PYTHONPATH = 'src'
python tools\explain_assignment_counterfactual.py `
  --dataset work\dataset_v21\beeline_synthetic_dataset_v2_1 `
  --scenario core `
  --input-plan work\planning\normatives-event-001-explained-v2.json `
  --job-id EAST-EVENT-001 `
  --engineer-id EAST-ENG-01 `
  --cache work\routing\exact-repair-search.sqlite3 `
  --transit-index work\transit\moscow_2026-08-17.sqlite `
  --output work\planning\counterfactual-EAST-EVENT-001-to-EAST-ENG-01.json `
  --max-route-checks 200 --execute
```

Ответ различает `FEASIBLE`, статическую недопустимость выбранной пары, запрет изменения начатой активности, отсутствие решения в локальном поиске, исчерпание лимита и непроверенные маршрутные данные. Для допустимого варианта возвращаются новое время, изменения назначений и метрик, вытесненные заявки и независимо проверенный гипотетический план.

Контрфактический артефакт всегда имеет `counterfactual_only: true` и `publication_allowed: false`: он объясняет последствия решения пользователя, но не заменяет операционную публикацию плана. Отсутствие варианта в ограниченном поиске не выдаётся за глобальное доказательство невозможности.

## Пересборка индекса

Исходный GTFS лежит в `A:\LCT2-routing\gtfs-inspect`, сохранённые ответы Яндекс Расписаний — в `work\transit_normal_weekday_mcc_v2`, схема метро — в `A:\LCT2-routing\research\mosmetro-api\schema.json`. Сборка выполняется один раз:

```powershell
python tools\build_local_transit_index.py `
  --gtfs A:\LCT2-routing\gtfs-inspect `
  --rail work\transit_normal_weekday_mcc_v2 `
  --metro-schema A:\LCT2-routing\research\mosmetro-api\schema.json `
  --output work\transit\moscow_2026-08-17.sqlite

python tools\build_surface_walk_transfers.py `
  --database work\transit\moscow_2026-08-17.sqlite

python tools\build_walk_transfers.py `
  --database work\transit\moscow_2026-08-17.sqlite
```

Последние две команды измеряют пешеходные переходы локально и записывают их в индекс. Их нужно запускать **последовательно** из-за блокировки записи SQLite. GPU не нужен.

Индекс содержит 1 649 396 участков наземного транспорта, 49 654 участка железнодорожных поездов и 77 006 рассчитанных вариантов движения между 278 станциями метро. По схеме метро сопоставлены все 31 станция МЦК и 139 станций МЦД. Три станции МЦК, отсутствовавшие в ответе API «расписание по станции», дополнены подтверждёнными отправлениями из 12 запросов к API поиска поездок между соседними платформами. Исходные ответы лежат в `work\transit_normal_weekday_mcc_v2\mcc_search_evidence`.

Для обновления железнодорожного расписания ключ Яндекс Расписаний нужен только во время сбора; бесплатный тариф ключа пользователя показывает 500 запросов в сутки. Текущий снимок уже собран. В пользовательском интерфейсе следует указать Яндекс Расписания как источник данных согласно [условиям API](https://yandex.ru/dev/rasp/doc/ru/). Состав API и тариф нужно перепроверять перед новым сбором.

## Ограничения и проверка

- В GTFS нет поправок на внеплановые отмены и фактические задержки. Обычное расписание может отличаться от движения в конкретный день.
- Для метро нет опубликованной полной таблицы отправлений на 17 августа. Ожидание 180 секунд — допущение сценария, а не «полученный поезд». Результат с метро должен оставаться помеченным как оценка.
- Для МЦК/МЦД используется нормальный понедельник 21 сентября. Время 17 августа по этому источнику нельзя выдавать за исторически подтверждённое.
- В смешанном маршруте расписания автобусов/поездов точные для своих источников, а участок метро остаётся модельным из-за отсутствия полной таблицы отправлений.
- Если покрытая сеть не даёт пути, ответ `UNKNOWN` не доказывает недоступность адреса.

Проверка кода: `$env:PYTHONPATH='src'; python -m pytest -q`. Манифест индекса содержит контрольные SHA-256 исходных файлов, дату сценария, эталонную дату поездов и статистику покрытия.
