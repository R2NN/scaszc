# Запуск на новом наборе данных

## Поддерживаемая граница

Новый набор должен соответствовать схеме `2.1.0` и содержать каталоги `common`, `core`, `stress`, `manifest.json` и `CHECKSUMS.sha256`. Количество районов, инженеров, заявок, событий и их ID не фиксировано.

Для замены значений удобнее скопировать текущий каталог `work/dataset_v21/beeline_synthetic_dataset_v2_1` как шаблон, изменить CSV/JSON и выполнить:

```powershell
$env:PYTHONPATH = 'src'
python tools\seal_planning_dataset.py --dataset D:\data\new-day --execute
python tools\validate_planning_dataset_generic.py --dataset D:\data\new-day
```

`seal_planning_dataset.py` не исправляет данные и не делает их истинными — он только фиксирует контрольные суммы после осознанного изменения. Строгий загрузчик затем проверяет схему и связи.

## Та же дата/территория, новые заявки и адреса

Новые координаты в Москве и ЦФО не требуют пересборки дорожных тайлов или транспортного индекса. Матрицы обязательно строятся заново:

```powershell
$env:PYTHONPATH = 'src'
python tools\run_new_dataset_pipeline.py `
  --dataset D:\data\new-day `
  --scenario core `
  --run-dir D:\runs\new-day-core `
  --transit-index work\transit\moscow_2026-08-17.sqlite `
  --warm-start D:\runs\previous-day\core-exact-repaired.json
```

Без `--execute` команда выводит точный план стадий. После проверки добавить `--execute`.

Для стандартного `http://127.0.0.1:8002` pipeline первой стадией проверяет
здоровье реального локального Valhalla и при необходимости запускает его в
Docker Desktop WSL. Перед запуском он генерирует config текущей схемы,
сохраняя пути к установленным tiles, и пересобирает CLI против установленной
версии Valhalla. Health-check содержит revision runtime, поэтому bridge со
старой несовместимой версией автоматически заменяется. Это не подменяет
маршрутизацию: если в WSL нет compiler, совместимого Valhalla или tiles,
запуск завершается ошибкой `UNAVAILABLE`.
Bridge держит три независимых постоянных Valhalla-worker вместо одной общей
очереди исполнения; число задаётся `VALHALLA_BRIDGE_WORKERS` в окружении WSL.
В `/status` видны `worker_count`, `available_workers` и `tile_revision`.
Pipeline добавляет ревизию дорожных тайлов к ключам кеша: после замены
тайлов старые маршруты не используются. Для внешнего сервиса без этого поля
необходимо задать `VALHALLA_TILE_REVISION` вручную.
Для внешнего endpoint либо нестандартного способа запуска можно передать
`--skip-valhalla-autostart`.

## Быстрый расчёт распределения без exact routing

Если для нужного дня уже есть полный каталог screening-матриц, распределение
можно посчитать и проверить без Valhalla:

```powershell
$env:PYTHONPATH = 'src'
python tools\solve_screening_zones.py --dataset D:\data\new-day --scenario core `
  --screening-root D:\data\new-day-screening --output D:\runs\screening.json `
  --seconds-per-tier 10 --coverage-first-only
python tools\validate_screening_solution.py --dataset D:\data\new-day `
  --scenario core --screening-root D:\data\new-day-screening `
  --candidate D:\runs\screening.json
```

При холодном старте поиск до 10 секунд на район сначала пытается уменьшить
число бригад при полном покрытии. Если полный план не получен, обычный
coverage-first поиск получает до 60 секунд. Оба лимита настраиваются через
`--cold-start-improve-seconds` и `--cold-start-seed-seconds`; `0` отключает
соответствующую фазу. CP-SAT отдельно проверяет найденный маршрутный порядок.
Проверка `validate_screening_solution.py` независимо сверяет покрытие,
допустимость назначений, окна, смены, время, дуги и общий запас оборудования.
Это проверка по screening-временам; `publication_allowed` остаётся `false`
до точной маршрутизации и независимой exact-валидации. Дата, районы, ID и
количество заявок в поиске не зашиты.

## Новая дата

Нужен GTFS, календарь которого активен на новую дату. Также требуются снимок железнодорожного расписания и схема метро. В пакет вложены исходники текущего эталонного запуска как пример:

Индекс строится по выбранной дате. Железнодорожный снимок сделан для понедельника, поэтому на другие дни недели он не переносится; остаются рейсы GTFS и модель метро с явно указанным ожиданием. Если исходники не содержат рейсов на дату, построение завершается ошибкой.

```powershell
python tools\run_new_dataset_pipeline.py `
  --dataset D:\data\new-date `
  --scenario core `
  --run-dir D:\runs\new-date-core `
  --rebuild-transit-index `
  --gtfs offline-assets\transit-sources\gtfs `
  --rail offline-assets\transit-sources\rail `
  --metro-schema offline-assets\transit-sources\metro\schema.json `
  --execute
```

Конвейер последовательно:

1. проверяет оба сценария без канонических количеств и ID;
2. при необходимости строит датированный транспортный SQLite-индекс;
3. рассчитывает пешеходные переходы Valhalla;
4. выполняет routing preflight;
5. достраивает CAR/BICYCLE/WALKING матрицы Valhalla пакетами только для
   недостающих координатных пар; холодные блоки считает параллельно;
6. строит PUBLIC_TRANSIT матрицы из локального индекса;
7. параллельно решает независимые районы, начиная с разреженного графа и расширяя его при необходимости;
8. фиксирует лучшее найденное покрытие и отдельным CP-SAT-запуском пытается уменьшить число бригад, не разрешая потерять заявку;
9. проверяет выбранные маршруты exact routing, возвращает измеренные длительности и no-good cuts в CP-SAT и пересчитывает только затронутые районы;
10. повторяет refinement до точного допустимого результата или исчерпания явного бюджета, затем независимо валидирует план;
11. пробует прямые вставки и цепочки переносов, только если после точной
    проверки остались неназначенные заявки;
12. пытается убрать целую бригаду, перенося её заявки только в уже задействованные бригады, и exact-проверяет только изменённые маршруты;
13. сохраняет `pipeline-run.json` с SHA-256 всех результатов.

Каждый запуск должен использовать новый пустой `run-dir`. Матрицы и результаты маршрутизации хранятся отдельно в контентно-адресуемом общем кеше (по умолчанию `.beego-cache` рядом с `run-dir`), поэтому старые результаты не смешиваются, но неизменившиеся координаты и запросы повторно не вычисляются. Каталог можно задать через `--shared-cache-dir`. Пешие и велосипедные дорожные маршруты при неизменных тайлах переиспользуются между датами; автомобильные и расписание общественного транспорта сохраняют зависимость от времени.

## Новая территория

Вложенная Valhalla покрывает Москву и Центральный федеральный округ. Для координат вне покрытия нужно собрать новые Valhalla tiles из актуального OSM PBF и заменить каталог `offline-assets/valhalla-data`. Подмена неизвестных маршрутов прямой линией запрещена: до появления покрытия результат должен оставаться `ROUTING_INCOMPLETE`.

## Что передавать UI

Передавать только последний JSON со статусом `EXACT_VALID`, `publication_allowed: true` и `validation.status: VALID`. Такой план может быть допустимым частичным планом: неназначенные заявки обязаны находиться в `plan.unserved_job_ids`. Полнота покрытия отражается отдельным полем `coverage_complete` и не подменяет решение о публикации. `pipeline-run.json` содержит `publishable_final_plan` и `candidate_plan`.

## Оценка времени

Построение матриц и точная маршрутизация — длительные операции. Их нужно запускать как фоновую задачу с прогрессом по стадиям `STAGE_START`/`STAGE_COMPLETE`. Событие `FIRST_VALID_PLAN` показывает первый уже точно проверенный публикуемый план, пока конвейер продолжает уменьшать число бригад; `STAGE_SKIPPED` отмечает пропущенные ненужные этапы. В манифесте есть `first_valid_plan` и время до него. Финальным остаётся `publishable_final_plan` после всех включённых стадий. Если необязательный этап улучшения завершается ошибкой, pipeline сохраняет предыдущий точно проверенный план и отмечает этап в `degraded_stages`, а не теряет допустимый результат. Повторный запуск использует координатный delta-кеш матриц, сохранённые метки кратчайших путей общественного транспорта и точные маршруты при совпадении координат, времени и идентичности транспортного индекса. Для CP-SAT можно передать предыдущий screening- или exact-план через `--warm-start`; неизвестные и новые ID безопасно отбрасываются из подсказки.

Если путь не указан, pipeline сам ищет лучший опубликованный `EXACT_VALID`
incumbent с совпадающими checksum, временем планирования и независимой
валидацией. Сравнение всегда лексикографическое: непокрытые срочные заявки,
непокрытые обычные заявки, число бригад, затем остальные метрики. Параметр
`--polish-seconds-per-tier` задаёт быстрый бюджет поиска меньшего числа бригад
на разреженном графе. Если он не улучшил incumbent, pipeline автоматически
делает ещё одну попытку на полном графе за
`--full-graph-polish-seconds` (по умолчанию 30 секунд на район); `0` отключает
этот fallback. В screening-артефакте сохраняются все попытки и их доказательства,
а в publication попадает результат только после exact routing и независимой
валидации.

Для coverage-first диагностики одной трудной заявки зональный probe поддерживает
`--force-assignment`, `--forbid-assignment`, `--hint-exact-plan` и
`--max-predecessors`. Сначала разрешается использовать все доступные бригады и
ищется ноль неназначенных заявок. Только после получения `EXACT_VALID` полного
плана запускается уменьшение числа бригад. Запрет пары инженер–заявка применяют
только после воспроизводимого точного нарушения окна; один screening-результат
не является основанием для такого запрета.

Обычный pipeline теперь включает exact-feedback по умолчанию и даёт ему до 20
итераций. При нарушении окна он запрещает повторять только проверенный точный
префикс маршрута, сохраняет остальные назначения и повторно решает затронутый
район с обязательным полным покрытием. Структурная подсказка получает заново
рассчитанные screening-времена; placeholder-времена из zero-travel артефактов
не используются. Флаг `--skip-route-conflict-refinement` отключает этот режим.
На всю стадию exact-feedback по умолчанию отведено 120 секунд
(`--refinement-wall-seconds`). После лимита конвейер точно проверяет лучший
доступный промежуточный маршрутный план и продолжает восстановление покрытия.

При наличии доказанных конфликтов сначала решается локальный временной кластер:
его ядро строится из текущей провалившейся заявки и её предшественника, а
размер ограничен 45 заявками. Несвязанные назначения и порядок незатронутых
маршрутов фиксируются, а дуги и допустимые исполнители локальной модели
сокращаются до нужных для поиска.
Если локальная модель не находит решение, выполняется fallback без этих
фиксаций. Незавершённый запуск можно продолжить с сохранёнными выводами через
`refine_screening_exact.py --initial-refinement-state ...`; checkpoint и новый
input-candidate обязательно должны относиться к тому же checksum датасета.

Внутри одного запуска refinement повторно использует точные результаты только
для неизменившихся маршрутов инженеров (тот же датасет, снимок screening,
порядок заявок и входные screening-времена). Неопределённые ответы маршрутизатора
проверяются заново. Для каждой зоны базовый граф и ограничения строятся один раз;
последующие итерации добавляют к нему только новые exact-длительности и отсечения.
Это ускоряет повторные итерации, не меняя критерии оптимизации. Перед публикацией
план всё равно проходит полную независимую exact-проверку.

Перед уплотнением бригад стадия `exact_chain_and_lns_repair` сначала выполняет
локальные цепочки вытеснений, затем exact-aware LNS. LNS разрушает ограниченный
временной кластер вокруг каждой неназначенной заявки и заново собирает несколько
затронутых маршрутов. Параметры `--lns-route-checks`, `--lns-beam-width`,
`--lns-max-destroyed-jobs` и `--lns-max-engineers` задают бюджет; каждое принятое
изменение полностью пересчитывается и проходит независимый валидатор.
Обычный запуск пропускает отдельную стадию прямых вставок: те же вставки уже
выполняет `exact_chain_and_lns_repair`. Для отдельной диагностической попытки
есть `--include-exact-improvement`. Каждый принятый и проверенный перенос сразу
сохраняется; при лимите стадии (`--optimization-wall-seconds`, по умолчанию 90)
конвейер берёт последний сохранённый план. Поиск одного нового переноса
ограничен 30 секундами, затем возвращает лучший проверенный результат.

Финальная стадия `exact_team_compaction` использует beam search с screening-
проверкой для удаления одного полного маршрута и только затем обращается к
exact routing. Она не активирует новую бригаду, не меняет набор непокрытых
заявок и принимает результат лишь после `EXACT_VALID`. Параметры pipeline
`--team-compaction-candidates` и `--team-compaction-states` ограничивают
поиск; `--skip-team-compaction` отключает эту оптимизацию. Каждый следующий
проход применяет delta к последнему принятому exact-плану, сохраняя удаления и
перестройки предыдущих проходов.
