# Запуск на новом наборе данных

## Поддерживаемая граница

Новый набор должен соответствовать схеме `2.1.0` и содержать каталоги `common`, `core`, `stress`, `manifest.json` и `CHECKSUMS.sha256`. Количество районов, инженеров, заявок, событий и их ID не фиксировано.

Для замены значений удобнее скопировать текущий каталог `work/dataset_v21/beeline_synthetic_dataset_v2_1` как шаблон, изменить CSV/JSON и выполнить:

```powershell
$env:PYTHONPATH = 'src'
python tools\seal_planning_dataset.py --dataset D:\data\new-day --execute
python tools\validate_planning_dataset_generic.py --dataset D:\data\new-day
```

`seal_planning_dataset.py` не исправляет данные и не делает их истинными — он только фиксирует контрольные суммы после осознанного изменения. Строгий загрузчик затем проверяет схему и связи.

## Та же дата/территория, новые заявки и адреса

Новые координаты в Москве и ЦФО не требуют пересборки дорожных тайлов или транспортного индекса. Матрицы обязательно строятся заново:

```powershell
$env:PYTHONPATH = 'src'
python tools\run_new_dataset_pipeline.py `
  --dataset D:\data\new-day `
  --scenario core `
  --run-dir D:\runs\new-day-core `
  --transit-index work\transit\moscow_2026-08-17.sqlite `
  --warm-start D:\runs\previous-day\core-exact-repaired.json
```

Без `--execute` команда выводит точный план стадий. После проверки добавить `--execute`.

Для стандартного `http://127.0.0.1:8002` pipeline первой стадией проверяет
здоровье реального локального Valhalla и при необходимости запускает его в
Docker Desktop WSL. Перед запуском он генерирует config текущей схемы,
сохраняя пути к установленным tiles, и пересобирает CLI против установленной
версии Valhalla. Health-check содержит revision runtime, поэтому bridge со
старой несовместимой версией автоматически заменяется. Это не подменяет
маршрутизацию: если в WSL нет compiler, совместимого Valhalla или tiles,
запуск завершается ошибкой `UNAVAILABLE`.
Для внешнего endpoint либо нестандартного способа запуска можно передать
`--skip-valhalla-autostart`.

## Новая дата

Нужен GTFS, календарь которого активен на новую дату. Также требуются снимок железнодорожного расписания и схема метро. В пакет вложены исходники текущего эталонного запуска как пример:

```powershell
python tools\run_new_dataset_pipeline.py `
  --dataset D:\data\new-date `
  --scenario core `
  --run-dir D:\runs\new-date-core `
  --rebuild-transit-index `
  --gtfs offline-assets\transit-sources\gtfs `
  --rail offline-assets\transit-sources\rail `
  --metro-schema offline-assets\transit-sources\metro\schema.json `
  --execute
```

Конвейер последовательно:

1. проверяет оба сценария без канонических количеств и ID;
2. при необходимости строит датированный транспортный SQLite-индекс;
3. рассчитывает пешеходные переходы Valhalla;
4. выполняет routing preflight;
5. строит CAR/BICYCLE/WALKING матрицы Valhalla;
6. строит PUBLIC_TRANSIT матрицы из локального индекса;
7. параллельно решает независимые районы, начиная с разреженного графа и расширяя его при необходимости;
8. фиксирует лучшее найденное покрытие и отдельным CP-SAT-запуском пытается уменьшить число бригад, не разрешая потерять заявку;
9. проверяет выбранные маршруты exact routing, возвращает измеренные длительности и no-good cuts в CP-SAT и пересчитывает только затронутые районы;
10. повторяет refinement до точного допустимого результата или исчерпания явного бюджета, затем независимо валидирует план;
11. пробует прямые вставки и цепочки переносов;
12. пытается убрать целую бригаду, перенося её заявки только в уже задействованные бригады, и exact-проверяет только изменённые маршруты;
13. сохраняет `pipeline-run.json` с SHA-256 всех результатов.

Каждый запуск должен использовать новый пустой `run-dir`. Матрицы и результаты маршрутизации хранятся отдельно в контентно-адресуемом общем кеше (по умолчанию `.beego-cache` рядом с `run-dir`), поэтому старые результаты не смешиваются, но неизменившиеся координаты и запросы повторно не вычисляются. Каталог можно задать через `--shared-cache-dir`.

## Новая территория

Вложенная Valhalla покрывает Москву и Центральный федеральный округ. Для координат вне покрытия нужно собрать новые Valhalla tiles из актуального OSM PBF и заменить каталог `offline-assets/valhalla-data`. Подмена неизвестных маршрутов прямой линией запрещена: до появления покрытия результат должен оставаться `ROUTING_INCOMPLETE`.

## Что передавать UI

Передавать только последний JSON со статусом `EXACT_VALID`, `publication_allowed: true` и `validation.status: VALID`. Такой план может быть допустимым частичным планом: неназначенные заявки обязаны находиться в `plan.unserved_job_ids`. Полнота покрытия отражается отдельным полем `coverage_complete` и не подменяет решение о публикации. `pipeline-run.json` содержит `publishable_final_plan` и `candidate_plan`.

## Оценка времени

Построение матриц и точная маршрутизация — длительные операции. Их нужно запускать как фоновую задачу с прогрессом по стадиям `STAGE_START`/`STAGE_COMPLETE`. Повторный запуск использует координатный delta-кеш матриц, сохранённые метки кратчайших путей общественного транспорта и точные маршруты при совпадении координат, времени и идентичности транспортного индекса. Для CP-SAT можно передать предыдущий screening- или exact-план через `--warm-start`; неизвестные и новые ID безопасно отбрасываются из подсказки.

Если путь не указан, pipeline сам ищет лучший опубликованный `EXACT_VALID`
incumbent с совпадающими checksum, временем планирования и независимой
валидацией. Сравнение всегда лексикографическое: непокрытые срочные заявки,
непокрытые обычные заявки, число бригад, затем остальные метрики. Параметр
`--polish-seconds-per-tier` задаёт быстрый бюджет поиска меньшего числа бригад
на разреженном графе. Если он не улучшил incumbent, pipeline автоматически
делает ещё одну попытку на полном графе за
`--full-graph-polish-seconds` (по умолчанию 30 секунд на район); `0` отключает
этот fallback. В screening-артефакте сохраняются все попытки и их доказательства,
а в publication попадает результат только после exact routing и независимой
валидации.

Финальная стадия `exact_team_compaction` использует beam search с screening-
проверкой для удаления одного полного маршрута и только затем обращается к
exact routing. Она не активирует новую бригаду, не меняет набор непокрытых
заявок и принимает результат лишь после `EXACT_VALID`. Параметры pipeline
`--team-compaction-candidates` и `--team-compaction-states` ограничивают
поиск; `--skip-team-compaction` отключает эту оптимизацию.
